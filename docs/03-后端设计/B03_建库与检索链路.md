## 二、切分算法（`chunk_text`）

```python
# app/chunking.py:11
def chunk_text(text: str, size: int, overlap: int) -> list[tuple[int, int, str]]:
    if not isinstance(size, int) or not isinstance(overlap, int):
        raise AppError("分块参数须为整数，且 0 <= chunk_overlap < chunk_size。")
    if size <= 0 or overlap < 0 or overlap >= size:
        raise AppError("分块参数须为整数，且 0 <= chunk_overlap < chunk_size。")

    result = []
    start = 0
    while start < len(text):
        end = min(start + size, len(text))
        result.append((start, end, text[start:end]))
        if end == len(text):
            break
        start = end - overlap
    return result
```

### 逐字追踪 `chunk_text("甲乙丙丁戊己庚辛壬癸", 6, 2)`

```
len(text) = 10, size = 6, overlap = 2
第1轮：start=0  → end=min(6,10)=6  → 记录 (0,6,"甲乙丙丁戊己")；end!=10 → start=6-2=4
第2轮：start=4  → end=min(10,10)=10 → 记录 (4,10,"戊己庚辛壬癸")；end==10 → break
结果：[(0,6,"甲乙丙丁戊己"), (4,10,"戊己庚辛壬癸")]
重叠：text[4:6] = "戊己" 共 2 字 ✅
```

这条断言就是 `tools/selfcheck.py` 里的第 1 项，也是骨架 `check_local.py` 的原始用例。

### 为什么 `start = end - overlap` 而不是 `start += size - overlap`

两者在「没到文末」时等价（`end = start + size`），但**到文末时不同**：
`start += size - overlap` 会在最后一段产生一个越界的 `start`，还得额外判 `start < len(text)`；
`start = end - overlap` 直接用上一轮真实的 `end`，文末那轮 `end == len(text)` 已经 `break`，
不存在越界。骨架用的就是后者，本项目保持一致。

### 边界情况

| 情况 | 结果 |
| --- | --- |
| `len(text) <= size` | 只有 1 个片段 `(0, len, text)` |
| `len(text) == size` | 同上，1 个片段 |
| `overlap == 0` | 每段严格不重叠，段数 `ceil(len/size)` |
| `overlap == size - 1` | 每段只前进 1 字，段数 ≈ `len - size + 1`（**教学上要提醒学生这会爆量**） |
| `size <= 0` 或 `overlap >= size` | 抛 `AppError`，文案固定 |

## 四、向量化两条通道

### 4.1 mock 通道（默认，无需网络）

```python
# app/embedding.py:58
def mock_embed_one(text: str, dim: int) -> list[float]:
    vector = [0.0] * dim
    for char in text:
        vector[_gram_hash(char, dim)] += 1.0            # 单字权重 1.0
    for i in range(len(text) - 1):
        vector[_gram_hash(text[i:i + 2], dim)] += 1.0   # 2-gram 权重 1.0
    for i in range(len(text) - 2):
        vector[_gram_hash(text[i:i + 3], dim)] += 0.25  # 3-gram 权重 0.25
    norm = math.sqrt(sum(v * v for v in vector))
    return [v / norm for v in vector] if norm else vector
```

`_gram_hash` 是 FNV-1a 32 位取模（`app/embedding.py:50`）：

```python
h = 2166136261
for ch in gram:
    h = ((h ^ ord(ch)) * 16777619) & 0xFFFFFFFF
return h % dim
```

**为什么不用内置 `hash()`**：Python 的字符串 `hash()` 受 `PYTHONHASHSEED` 影响，
同一个词在不同进程里哈希值不同，会导致「今天建的库明天检索不到」。
FNV-1a 是纯算术，跨进程、跨机器稳定。

**为什么是三通道加权 1 / 1 / 0.25**：这是实测调出来的。
只用 2-gram 时，T01「读书会通常在每周几几点举行？」检索不到 `D01-C001`（排第 4），
T05「讨论空间需要几人每次最长多久？」也偏；加入单字通道后 10 题的证据文件全部进入前 3。
3-gram 权重压到 0.25 是为了「长词有加成但不主导」，经 63 组网格搜索确定，
详见 `docs/03-后端设计/B06_离线模拟通道设计.md`。

### 4.3 分批

`store.build_index` 按 `cfg["embedding_batch_size"]`（默认 8）分批：

```python
for i in range(0, len(chunks), batch):
    part = embedding.embed_texts(cfg, key, [c["text"] for c in chunks[i:i + batch]])
    vectors.extend(part)
    if progress:
        progress(done=len(vectors), total=len(chunks))
```

15 片段 → 2 批（8 + 7）。分批的意义：
1. 教师接口常有单次请求体积上限，一次发 15 个片段可能 413；
2. 进度条能真实反映「已经向量化了几个片段」。

### 5.1 余弦相似度

```python
# app/retrieval.py:10
def cosine(a: list[float], b: list[float]) -> float:
    if not a or not b or len(a) != len(b):
        raise AppError("向量维度不一致，无法比较。")
    scale = max(max(abs(v) for v in a), max(abs(v) for v in b))
    if scale == 0:
        return 0.0
    an = [v / scale for v in a]
    bn = [v / scale for v in b]
    dot = math.fsum(x * y for x, y in zip(an, bn))
    na = math.sqrt(math.fsum(x * x for x in an))
    nb = math.sqrt(math.fsum(y * y for y in bn))
    if na == 0 or nb == 0:
        return 0.0
    return dot / (na * nb)
```

**先除 `scale` 再算**：如果向量里出现 `1e308`，`x*x` 会溢出成 `inf`，余弦就变 `nan`。
先按最大绝对值缩放，让所有分量落在 [-1, 1]，平方绝不会溢出。
`tools/selfcheck.py` 里有一条断言就是 `cosine([1e308,1e308],[1e308,1e308])` 必须是有限值且 ≈ 1.0。

**用 `math.fsum` 而不是 `sum`**：`fsum` 用 Kahan 求和，长向量累加精度更高。
256 维时两者差异在 1e-16 量级，但换成教师接口的 1536 维就会显现。

### 5.2 全量排名（`rank_all`）

```python
# app/retrieval.py:42
def rank_all(chunks, query_vector) -> list[dict[str, Any]]:
    scored = _scored(chunks, query_vector)        # 在副本上打分，不改原 chunks
    scored.sort(key=lambda chunk: (-chunk["score"], chunk["chunk_id"]))
    for position, chunk in enumerate(scored, start=1):
        chunk["rank"] = position
    return scored
```

三个细节：

1. **`_scored` 在副本上工作**：`[dict(c) for c in chunks]`，绝不改 `index.json` 里的原始顺序。
   若直接改原列表，第二次检索的「全量排名」会基于上一次排好的顺序，结果不可复现。
2. **`-chunk["score"]` 实现降序**：`sort` 只接受升序 key，取负是最省事的降序写法。
   等价写法是 `reverse=True`，但那样就没法加次级键了。
3. **次级键 `chunk_id`**：得分完全相同时（mock 通道下确实会出现），按编号升序保证结果稳定可复现。

### 5.3 前 k 截取（`split_trace`）

```python
# app/retrieval.py:51
def split_trace(trace, k) -> tuple[list[dict], list[dict]]:
    hits = trace[:k]
    for chunk in trace:
        chunk["retrieved"] = chunk["rank"] <= k
    return hits, trace
```

**返回两份数据**：`hits`（前 k 条，进提示词）与 `trace`（全 15 条，进「检索过程」表格）。
这就是任务4 验收第③项「检索过程全部片段按得分降序、能看出前 k 个」的实现——
表格里 `retrieved=true` 的 3 行加浅底纹，第 3 行加虚线，其余 12 行正常显示。

## 七、`data/` 六份资料的检索竞争关系

实测 T03「普通图书最多同时借阅几本借多久？」的 top-3 是
`D04-C002`（0.5147）→ `D04-C003`（0.4686）→ `D02-C001`（0.4677）。

**正确答案所在的 `D02-C001` 只排第 3**，因为 04 号资料里也有「借阅」「普通图书」等词。
这正是 mock 档要点抽取机制存在的理由：`llm.mock_answer` 不按排名先后抽句，
而是**遍历所有 hits，找同时含某个要点全部 `must` 词的句子**。
`D02-C001` 含「4本普通图书」与「21天」，命中「借阅数量」「借期」两个要点，于是被选中并标 `[D02-C001]`。

换句话说：**检索负责「把可能的片段捞进来」，要点抽取负责「从里面挑对的那句」**。
这也是为什么 k 不能太小——`D02-C001` 排第 3，k=1 或 k=2 就捞不到它。
