## 二、其它服务的账号密码

| 服务 | 地址 | 账号 | 密码 | 出处 |
|---|---|---|---|---|
| MySQL | `127.0.0.1:3306` | `root` | `asdfghjkl54321` | `deploy/local-mysql.env` |
| **Milvus（向量库）** | `127.0.0.1:19530` | `root` | 见 `MILVUS_PASSWORD` | `deploy/milvus/user.yaml` 已开 `authorizationEnabled: true`；密码在 `deploy/local-mysql.env` |
| **Attu（Milvus 管理界面）** | `http://localhost:3000` | 见 `ATTU_ADMIN_USER` | 见 `ATTU_ADMIN_PASSWORD` | Attu **自己**的账号（容器 `/data/attu.db` 的 `app_users` 表），与 Milvus 无关 |
| MinIO 控制台 | `http://127.0.0.1:9001` | `minioadmin` | `minioadmin2026` | `deploy/milvus/docker-compose.yml` |

> **注意**：`asdfghjkl54321` 是 **MySQL root 的密码**，只用来连 3306，跟应用登录的 `admin` / `user` 完全无关。
> 在 5173 登录页填它是登不进去的。
>
> **Attu 和 Milvus 是两套账号，混用会登不进去**（v3 起 Attu 自带账号体系）：
>
> | | Attu 账号 | Milvus 账号 |
> |---|---|---|
> | 用途 | 登录 Attu 网页 | 客户端连 Milvus |
> | 存哪 | `/data/attu.db` → `app_users` | Milvus 元数据 |
> | 改法 | 首次打开页面建 / 直接改 attu.db | `tools/setup_milvus_auth.py --set-password` |
>
> - **第一次打开 `localhost:3000` 显示「Create admin account」是正常的**：那是要你建 Attu 的第一个管理员，
>   不是 Milvus 账号。密码要求 8–128 字符，且大写/小写/数字/符号四类至少占三类。
>   `app_users` 里一旦有记录，这个页面就变成普通的「Sign in」。
>
> **⚠️ 手改 `app_users` 会掉进坑里（ERR_TOO_MANY_REDIRECTS）**：Attu 的会话不是「有 session 就行」。
> 一次成功的认证需要三张表同时正确，缺任一项都会被弹回 `/login`，浏览器表现为**重定向死循环**：
>
> | 表 | 作用 | 缺了会怎样 |
> |---|---|---|
> | `app_users` | 账号本体（`password_hash` 是 `scrypt$<salt>$<base64url>`） | 登录失败 |
> | `tenants` | 租户；默认已有 `tenant_default` | — |
> | `tenant_memberships` | **用户与租户的关系**（`role=owner/admin/user`） | **没有它 session 解析返回 null → 无限重定向** |
> | `auth_sessions` | 会话；`id` 存的是 **`sha256(token)`**，不是 token 明文 | session 永远匹配不上 |
>
> 所以**不要手改数据库建账号**。正确做法是打开 `localhost:3000` 用「Create admin」页面创建，
> 它会自己把 user + membership 一起建好。若已被改坏，清空 `app_users` / `tenant_memberships` /
> `auth_sessions` 三张表后重新打开页面即可回到创建页。
>
> **Attu 登录成功但仍然「连接不可用」怎么办**：这是另一种错误，与登录无关。
> Attu 要给每个 Milvus 连接单独保存凭据，存在 `connections` 表（字段 `username` / `password` / `token`）。
> 如果那张表里的 `username` 是**空字符串**（早期自动创建的连接会这样），Attu 就会拿空用户名去连，
> Milvus 返 `16 UNAUTHENTICATED: missing ...`，界面显示"连接不可用"。
>
> 两种修法（选一）：
>
> 1. **界面上改（推荐）**：`连接不可用` 卡片右侧点**铅笔图标** → 填 Username `root`、
>    Password 为 Milvus 当前密码 → 保存 → 点「重试连接」。
> 2. 命令行改：确认 `connections.username` 为 `root`、`password` 与 `MILVUS_PASSWORD` 一致，
>    并把 `milvus_version` 置 null 强制重新探测。
>
> 验证凭据本身没问题（在宿主执行）：
>
> ```powershell
> python tools/setup_milvus_auth.py --verify
> ```
>
> - **改 env 文件里的密码不会改掉已存的密码**——env 只是配置来源。Milvus 要跑 `--set-password`，
>   Attu 要在页面上改连接凭据。
> - **Milvus 默认密码是 `Milvus`，不是空字符串**（镜像内 `milvus.yaml` 的
>   `common.security.defaultRootPassword`）。网上「默认密码为空」指旧版本；
>   按空密码连只会得到 `code=2 Fail connecting to server`，看不出真实原因。
> - `authorizationEnabled` 是**热加载**的（改 `user.yaml` 约 10 秒生效，不用重启容器），
>   所以顺序必须是「**先关着鉴权设好密码 → 再打开鉴权**」，反了会把自己锁在门外。
>
> ```powershell
> grep -E "MILVUS_PASSWORD|ATTU_ADMIN" deploy/local-mysql.env   # 看当前密码（该文件已 gitignore）
> python tools/setup_milvus_auth.py --status                    # 看 Milvus 鉴权状态与哪个密码能进
> python tools/setup_milvus_auth.py --set-password              # 改 Milvus 密码
> python tools/setup_milvus_auth.py --verify                    # 新密码能连 + 默认密码被拒
> ```

### 3.2 第二步：Milvus（19530，含 etcd / minio / attu）

**必须先起 Docker Desktop**，否则 `docker ps` 会报
`failed to connect to the docker API at npipe:...\pipe\dockerDesktopLinuxEngine`。

然后起 Milvus 这一套（4 个容器）：

```bash

# 确认状态（milvus 首次启动要建 meta、连 etcd/minio，约 40–60 秒才 healthy）
docker ps --filter "name=xi-" --format "{{.Names}} | {{.Status}} | {{.Ports}}"
```

期望看到：


### 3.3 第三步：Python AI 服务（8000）

**必须用真实 provider 模式启动**，否则会走 mock，回答固定是「这是针对『…』的模拟回答」。

一条命令（已封装好，直接跑）：

```bash

```

它做的事：读 `test-artifacts/p7-env.json` 拿 `INTERNAL_TOKEN`，注入
`AI_PROVIDER=real` + embedding-3 / glm-4-flash 的地址和 key + `MILVUS_URI=http://127.0.0.1:19530`，
然后用 uvicorn 拉起 `server-ai/app/main.py`。

**验证**（`INTERNAL_TOKEN` 从上一步那个 json 里取）：

```bash
TOK=$(python -c "import json;print(json.load(open('test-artifacts/p7-env.json',encoding='utf-8'))['INTERNAL_TOKEN'])")
curl -s -H "X-Internal-Token: $TOK" http://127.0.0.1:8000/internal/v1/health
```

期望：

```json
{"code":0,"data":{"status":"UP","embedding_model":"embedding-3","llm_model":"glm-4-flash", ...}}
```

> 这里的 `embedding_model` / `llm_model` 必须是**真实名字**。如果看到 `mock-embedding` / `mock-model`，
> 说明还在 mock 档，回答会是模板文案。

**手动起也行**（等价，但要自己带上全部环境变量）：

```bash
cd server-ai
AI_PROVIDER=real \
EMBEDDING_ENDPOINT=https://open.bigmodel.cn/api/paas/v4 \
EMBEDDING_MODEL=embedding-3 \
EMBEDDING_API_KEY=<你的智谱 key> \
```

### 3.4 第四步：Java 后端（8080）

先确认 jar 是最新的。**源码改过就必须重新打包**，否则跑的还是旧代码：

```bash
cd server-java
mvn -q -DskipTests "-Dspotless.check.skip=true" "-Dspotless.apply.skip=true" package
cd ..
```

> 打包前要先停掉正在跑的 Java，否则 Windows 会锁住 jar，报
> `Unable to rename '...jar' to '...jar.original'`。

启动：

```bash
PYTHONIOENCODING=utf-8 python test-artifacts/_dev_up_java.py
```

它读同一份 `p7-env.json`，把 MySQL 地址、`AUTH_JWT_SECRET`、`INTERNAL_TOKEN`、
bootstrap 账号（`admin` / `user`）、`STORAGE_ROOT` 全部注入，再 `java -jar`。

> **启动前先确认 8080 没被占**：Spring 发现端口占用会直接 `APPLICATION FAILED TO START` 退出，
> 不会自动换端口。之后浏览器就是「127.0.0.1 已拒绝连接」。查占用：
> `netstat -ano | findstr ":8080" | findstr LISTENING`，然后 `taskkill /PID <PID> /T /F`。

**验证**（**必须用这个路径，别用根路径** —— 8080 根路径没有路由，会返回 500）：

```bash
curl -s http://127.0.0.1:8080/api/v1/health
# {"code":0,"message":"success","data":{"status":"UP"}, ...}
```

**验证登录**：

```bash
curl -s -X POST http://127.0.0.1:8080/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"Admin@123456"}'
# {"code":0,"data":{"token":"eyJ...","user":{"username":"admin","id":6},...}}
```

> 注意响应里的 `user` 只带 `id` / `username` / `createdAt` 这几个字段，**不含 `role`**。
> 别拿 `role` 是否存在来判断登录成功，看 `code == 0` 和 `token` 非空即可。

### 3.5 第五步：前端（5173）

```bash
cd frontend
VITE_USE_MOCK=false VITE_PROXY_TARGET=http://127.0.0.1:8080 npx vite --host 127.0.0.1 --port 5173
```

浏览器打开 **http://127.0.0.1:5173/login**，用 `admin` / `Admin@123456` 登录。

两个环境变量的作用：

- `VITE_USE_MOCK=false` —— 关掉 MSW，让请求真的打到后端。`.env.development` 里默认是 `true`，
  不覆盖的话整个前端跑在假数据上（能点能看，但和数据库无关）。
- `VITE_PROXY_TARGET` —— Vite 把 `/api/**` 转发到哪。`vite.config.ts` 里默认 `http://localhost:8080`，
  显式写成 `127.0.0.1` 可以避开某些机器上 `localhost` 解析到 IPv6 导致代理连不上的问题。

## 五、启动失败排查

| 现象 | 原因 | 处理 |
|---|---|---|
| `docker ps` 报 `npipe ... 系统找不到指定的文件` | Docker Desktop 没启动 | 按 3.2 拉起它，等 10–20 秒 |
| **浏览器 8080 报 `ERR_CONNECTION_REFUSED`** | **Java 已退出。最常见是上一个进程没退干净，新进程报 `Port 8080 was already in use` 后自杀** | **见下方「8080 端口被占用」专项** |
| **浏览器 8000 看到 `{"detail":"Not Found"}`** | **这不是故障。Python AI 没有根路由，`GET /` 本来就 404** | **改用 `/internal/v1/health` + `X-Internal-Token` 验证（见 3.3）** |
| Java 起来但 8080 报 500，日志有 Flyway 错 | MySQL 没起或密码不对 | 检查 3306 与 `MYSQL_PASSWORD` |
| 登录返回 401 `用户名或密码错误` | 账号不存在或密码不符 | 用本文第一节的 `admin` / `user`；`demo` 永远失败 |
| 问答回答是「这是针对…的模拟回答」 | AI 服务在 mock 档 | 确认 `embedding_model` 是 `embedding-3` 不是 `mock-embedding` |
| 问答一直降级 / 50301 | Java 与 Python 的 `INTERNAL_TOKEN` 不一致 | 两边都从同一份 `p7-env.json` 取 |
| 建库报 `MILVUS_URI` 相关错 | `pymilvus` 没装 | `python -m pip install "pymilvus>=2.5"` |
| 前端能用但数据是假的 | `VITE_USE_MOCK` 还是 `true` | 按 3.5 显式传 `VITE_USE_MOCK=false` |
| `mvn package` 报 `Unable to rename ...jar` | jar 被运行中的 Java 占用 | 先停 Java 再打包 |
| 页面打开一片空白 | 5173 没起或端口被占 | `netstat -ano \| findstr :5173` |

### 8080 端口被占用（`ERR_CONNECTION_REFUSED` 的头号原因）

这个坑实际踩过：Java 日志里明确写着

```
APPLICATION FAILED TO START
Web server failed to start. Port 8080 was already in use.
```

Spring 发现端口被占会**直接退出**，不会自动换端口。于是前一个进程也已消失，端口彻底空着，
浏览器就看到「127.0.0.1 已拒绝连接」。

三步处理：

```bash
# 1) 看谁占着 8080
netstat -ano | findstr ":8080" | findstr LISTENING
#    最后一列是 PID

# 2) 杀干净（/T 连子进程，/F 强制）
```

```bash
for p in 3306 19530 8000 8080 5173; do
```

## 七、停止服务

```bash
# 前端 / 后端 / AI：停掉对应的终端，或按 PID 杀
# 注意顺序：先停前端，再停 Java，最后停 AI
netstat -ano | findstr ":5173" | findstr LISTENING   # 查 PID
taskkill /PID <pid> /T /F

# Milvus 一套（保留数据卷）
docker compose -f deploy/milvus/docker-compose.yml down

# MySQL 是 Windows 服务，一般不用停
net stop MySQL80
```

>`down` 不会删数据卷（`etcd_data` / `minio_data` / `milvus_data`），下次 `up -d` 数据还在。
>要彻底清空加 `-v`：`docker compose -f deploy/milvus/docker-compose.yml down -v`。
