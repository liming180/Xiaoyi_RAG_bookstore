## P0 · 开场自检

**作用**：LLM 很容易"假装读过"。这段用两个具体数字做探针，答错就说明它在编。

```text
接下来我要你做架构评审，但在你动笔之前，先做一个自检。

请读这两个文件：
1. docs/03-架构评审/snapshot/架构快照.md
2. docs/03-架构评审/01_企业级基线.md

读完只回答三个问题，不要展开，不要评审：

Q1 快照里记录的「对外端点」一共几个？
Q2 Java 主源码文件和测试文件各多少个？
Q3 基线里 D4（安全与权限）拿 3 分需要满足什么条件？用一句话说。

答完等我确认。如果某个数字你找不到，直接说「找不到」，不要推测。
```

**怎么判断它有没有真读**：

- Q1 正确答案：**28**
- Q2 正确答案：**111 / 2**
- Q3 应该提到「标准认证（JWT/OAuth2）+ 过期与刷新、授权按资源校验、密钥走环境变量、全量入参校验、速率限制」

三个都对，往下走。有错，重开一个会话——它已经污染了上下文。

## P1 · 架构符合性评审

**这是主提示词。** 三份材料一次给全，缺一份效果减半。

```text
你是一位有 15 年经验的后端架构师，正在对一个项目做技术尽职调查（technical due diligence）。
你的任务不是夸，是找差距。任何没有证据的结论都会被直接删除。

## 第一步：按顺序读这四个文件，全部读完再动笔

1. docs/03-架构评审/snapshot/架构快照.md
   —— 代码库的机械事实：三端规模、Java 分层、28 个对外端点、8 个内部端点、
      依赖清单、Flyway 迁移、测试现状、反模式扫描（超长文件/import 环/分层越界/全局状态/硬编码凭据）

2. docs/03-架构评审/01_企业级基线.md
   —— 8 维度评分标准（D1 分层 / D2 契约 / D3 数据 / D4 安全 / D5 可观测 / D6 容错 / D7 可测 / D8 交付），
      每一档都写明「什么证据才算」

3. docs/02-重构设计/00_项目架构规格.md
   —— 项目文档「声称」的架构：三端拓扑、架构铁律、接口契约、里程碑

4. docs/api/openapi-public.yaml
   —— 只读 paths 和 components.schemas 的字段名，不用逐行读 schema 定义

## 第二步：输出三部分，顺序不能变

### 第 1 部分 · 声明 vs 实际 差距表

把「文件 3 声称的」和「文件 1 实际存在的」逐条对齐：

| 声明内容 | 实际状态 | 是否一致 | 证据 |
| --- | --- | --- | --- |

「证据」列必须写 `文件路径:行号` 或快照章节号（如 §9.3）。
给不出证据的行，写「无法验证」，不要猜。

### 第 2 部分 · 8 维度打分

对 D1–D8 每项给 0–3 分，格式固定：

**D1 分层与依赖方向：X/3**
- 加分证据：（引用文件路径或快照章节）
- 扣分证据：
- 与满分（3 分）的具体差距：

八项打完，给总分 X/24。

### 第 3 部分 · 三个最严重的问题

只选三个。每个用这个结构：

- **问题**：一句话说清
- **证据**：文件路径:行号
- **触发条件**：什么情况下会真的出事（写具体操作，例如"用户 A 登录后把请求里的 id 改成 B 的"）
- **爆炸半径**：影响哪些功能、哪些数据
- **修法**：具体到「改哪个文件、拆成什么、先做哪一步」，不要写"建议优化"

## 约束（违反即作废）

1. 禁止出现「整体不错」「建议完善」「可以考虑」「值得肯定」这类无信息量的表述。
2. 每条结论必须能追溯到快照章节号或具体文件行号。
3. 不确定的写「需要人工核实：<具体核实什么>」，绝对不要编。
4. 不要给「加注释」「补充文档」这类不解决结构问题的建议。
5. 全文控制在 1500 字以内。宁可少说，不要注水。

## 额外要求（这条最重要）

如果发现「同一个仓库里同类代码有两种做法」，单独列出来。
例如：会话模块做了租户隔离、资料模块没做——这类不一致比单点 bug 更能说明架构问题。
```

## P5 · 重构前后对比

**场景**：改完代码后验收。先跑 `python tools/arch_snapshot.py`，再 `git diff`。

```text
以下是同一个项目重构前后的架构快照 diff：

（粘贴 git diff docs/03-架构评审/snapshot/架构快照.md 的输出）

请判断三件事：

1. 哪些指标变好了？哪些变坏了？逐条列出，带 diff 里的具体数字。
2. 有没有「表面变好、实际变坏」的情况？例如：
   - 文件数减少，但其实是大文件合并
   - 测试数增加，但都是 getter 测试
   - 端点数减少，但功能被藏到了别处
3. 一句话给这次重构下结论：值得做 / 白做了 / 做了一半。

不要客套。如果 diff 显示没有任何实质改善，直接说「这次重构没有解决任何架构问题」。
```

## 一句话

**P1 是主线，P0 是保险，P4 是应急。** 先跑 P0 确认它真读了，再跑 P1 拿结论，P2/P3 按需展开。
