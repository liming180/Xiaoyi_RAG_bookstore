# 企业级架构评审基线

> 用途：作为 LLM 评审的判据（rubric）。每个维度 0–3 分，满分 24。
> 原则：**"企业级"不是形容词，是一组可核对的属性。** 每一条都必须能指向代码或配置。

---

## 怎么用

1. 把本文件和 `snapshot/架构快照.md` 一起给 LLM。
2. 要求它逐维度打分，**每分必须给证据**（文件路径:行号，或快照章节号）。
3. 给不出的分，默认按低一档处理——这是防注水的硬约束。

**关于满分**：24 分是"一个成熟企业团队维护三年"的水准。本仓库是教学项目，**合理目标是 14–17 分**，把 D1/D2/D7 拉到 3 分、D4/D8 到 2 分即可。追求 D5/D6 满分属于过度工程。

## D1 · 分层与依赖方向 ★★★

**核心问题：依赖是否单向？层是否真的承担了职责？**

| 分 | 标准 |
| ---: | --- |
| 3 | 依赖严格单向（controller → service → repository → model）；无越层调用；无 import 环；单文件 < 400 行；跨端调用有独立 client 层 |
| 2 | 分层存在但有个别越层（如 controller 直连 repository）；存在 1–2 个超长文件 |
| 1 | 分层只是目录名，业务逻辑散落在 controller 或入口文件；存在循环依赖 |
| 0 | 无分层，或全部逻辑集中在一个入口文件 |

**证据采集**：快照 §2（分层文件分布）、§9.1（超长文件）、§9.2（import 环）、§9.3（越界）

**本仓库实测：2 分**

- ✅ `controller(10) / service(19) / repository(11) / model(45) / client(12)` 五层齐备，方向基本正确
- ❌ `AuthController` 直接 import repository，跳过 service（快照 §9.3）
- ❌ `server-ai/app/services/state.py` 反向 import `app.main`（快照 §9.3）
- ❌ `IndexServiceImpl` 730 行、`ChatServiceImpl` 533 行（快照 §9.1）
- ❌ Python 侧**没有分层**：8 个路由 + 全部业务逻辑 + mock 数据都在 `main.py`，`app/api/` 是空包

**常见误判**：看到目录叫 `service/` 就认为分层完成。要看 service 里是不是只做转发——如果 controller 里有业务分支，分层就是假的。

## D2 · 契约治理 ★★★

**核心问题：接口定义有没有唯一事实来源？三端会不会各改各的？**

| 分 | 标准 |
| ---: | --- |
| 3 | OpenAPI/Protobuf 单一来源；各端由契约**生成**类型而非手写；契约变更走 review；有契约测试 |
| 2 | 有完整 OpenAPI 文档且与实现基本一致，但类型靠手写同步 |
| 1 | 有接口文档但是事后补的，与实现有漂移 |
| 0 | 无契约文档，靠读代码猜 |

**证据采集**：`docs/api/openapi-public.yaml`、`openapi-internal.yaml`、快照 §3/§4（实际端点）

**本仓库实测：3 分**

- ✅ `openapi-public.yaml`（67 KB）+ `openapi-internal.yaml`（29 KB）+ `envelope.schema.json` + `error-codes.md`
- ✅ 前端 `openapi-typescript` 从契约生成类型（`npm run gen:api`）
- ✅ 统一响应信封 `{code, message, data, timestamp}`，错误码集中定义
- ⚠️ 唯一缺口：无自动化契约测试（实际端点 vs 契约文件的一致性校验）

这是全仓库最强的一项，可以直接作为答辩亮点。

## D3 · 数据与事务 ★★

**核心问题：schema 变更可追溯吗？事务边界对吗？测试数据有没有混进生产迁移？**

| 分 | 标准 |
| ---: | --- |
| 3 | 迁移版本化且幂等；无种子数据进迁移；事务边界明确（@Transactional 位置正确）；有索引设计说明；大表有分页策略 |
| 2 | 迁移版本化；有少量 demo 数据混在迁移里；事务靠默认 |
| 1 | 手工改表，或迁移不可重放 |
| 0 | 无迁移机制 |

**证据采集**：快照 §6（Flyway 清单）、`src/main/resources/db/migration/*.sql`

**本仓库实测：2 分**

- ✅ Flyway V1–V6 版本化，6 个迁移文件
- ❌ `V6__demo_user.sql` 把演示账号写进迁移——生产环境会凭空多一个账号
- ⚠️ 需核对：`@Transactional` 是否覆盖了「写消息 + 更新会话」这类跨表操作

**修法**：demo 数据移到 `db/seed/` 或 test profile 的 `data.sql`，迁移只管结构。

## D4 · 安全与权限 ★★★

**核心问题：认证是真的吗？密钥在哪？越权能防住吗？**

| 分 | 标准 |
| ---: | --- |
| 3 | 标准认证（JWT/OAuth2）+ 过期与刷新；授权按资源校验（不能改别人 ID 就读别人数据）；密钥走环境变量/密钥管理；全量入参校验；有速率限制 |
| 2 | 认证可用但简化（如无刷新、无黑名单）；授权靠 userId 过滤；密钥外置 |
| 1 | 认证是桩（内存 token、固定账号、无验签）；密钥有硬编码 |
| 0 | 无认证 |

**证据采集**：快照 §9.6（硬编码凭据）、`AuthInterceptor.java`、`pom.xml` 是否有 security 依赖

**本仓库实测：1 分** —— 这是最该优先修的一项

- ❌ `AuthInterceptor` 是内存 `ConcurrentHashMap`，构造时硬塞 `demoTokens.put("dev-token", 1L)`——**一个永不过期的后门 token**
- ❌ `pom.xml` 无 `spring-boot-starter-security`，无 JWT 库，token 不验签、不校验过期
- ❌ `XiaoyiProperties.internalToken = "dev-internal-token"` 硬编码默认值
- ❌ `frontend/src/api/modules/auth.ts:13` 写死 `username: 'demo', password: 'demo'`
- ❌ Python 侧内部令牌是静态字符串比对，无时间窗、无重放防护

**注意**：教学项目用简化认证可以接受，但**必须显式标注为已知限制**，而不是当成已完成。评审时这一项给 1 分是诚实的，给 3 分是自欺。

## D5 · 可观测性 ★★

**核心问题：线上出问题，你靠什么定位？**

| 分 | 标准 |
| ---: | --- |
| 3 | 结构化日志（含 traceId）+ 指标（Prometheus）+ 分布式追踪（OpenTelemetry）+ 健康检查分级（liveness/readiness） |
| 2 | 结构化日志 + 基础指标 + actuator health |
| 1 | 只有 print/console.log 或默认日志，无指标 |
| 0 | 无任何日志 |

**证据采集**：`pom.xml` 是否有 micrometer-registry-prometheus、日志配置、`/actuator/health`

**本仓库实测：1 分**

- ✅ `spring-boot-starter-actuator` 存在，docker-compose 用了 `/actuator/health` 做健康检查
- ❌ 无 `micrometer-registry-prometheus`，无指标暴露
- ❌ 无链路追踪，跨 Java → Python 的调用断了就没法串起来
- ⚠️ Python 侧无结构化日志

**常见误判**：有 actuator 就等于可观测性。actuator 只给了健康检查，没有业务指标和链路。

**对本项目**：这一项做到 2 分性价比很低，建议明确写"不做"，答辩时说明取舍理由反而加分。

## D6 · 容错与可靠性 ★★

**核心问题：下游挂了会怎样？重复请求会重复扣款/重复建库吗？**

| 分 | 标准 |
| ---: | --- |
| 3 | 超时 + 重试（指数退避）+ 熔断 + 降级；关键操作幂等（幂等键/去重表）；有背压或队列 |
| 2 | 有超时和降级，无熔断；幂等靠数据库唯一索引 |
| 1 | 有超时，失败直接 500 |
| 0 | 裸调用，无超时 |

**证据采集**：`WebClientConfig`（超时配置）、`MockAiClient`/`RealAiServiceClient`（降级逻辑）、`IndexTaskPoller`

**本仓库实测：2 分**

- ✅ `RealAiServiceClient` 自带完整超时体系：`connectTimeout`（第 53 行）+ 每调用独立 timeout（chat 用 `readTimeoutMs`、ingest 提交用 `ingestSubmitTimeoutMs`、状态查询用 `statusTimeoutMs`）
- ✅ `getWithRetry`（第 136 行）对状态查询类接口做重试，并用 `NonRetryableAiException` 区分「不该重试」的错误——这个细节比多数生产代码做得好
- ✅ 有 `degraded` 标志位和 mock 降级通道（设计上考虑了）
- ❌ 无 `resilience4j`，AI 服务连续失败不会熔断，会持续打满
- ❌ 建库任务是串行 + 轮询，无幂等键——重复点"重建"可能起多个任务
- ⚠️ `WebClientConfig` 是个空壳：`@Configuration` 但零个 `@Bean`，只有「J6 填充」的注释。真实客户端在 `RealAiServiceClient` 里自建连接池，导致这个类纯属误导性死代码，应删除或真正承担配置职责

**常见误判**：看到 `WebClientConfig` 就以为超时配好了。实际配置在客户端内部，配置文件是空的——**评审必须打开文件看，不能靠类名推断**。

## D7 · 可测试性 ★★★

**核心问题：测试是真的覆盖了核心路径，还是只有几个冒烟？**

| 分 | 标准 |
| ---: | --- |
| 3 | 单测覆盖 service 核心分支；集成测试覆盖 controller（MockMvc）；契约测试；测试可在 CI 无人值守跑；覆盖率有门槛 |
| 2 | 有单测但只覆盖部分 service；有集成测试；可本地一键跑 |
| 1 | 测试很少（<10% 文件），或只测了 getter |
| 0 | 无测试 |

**证据采集**：快照 §7（测试文件数 vs 主源码数）、`src/test/java/`、`frontend/test/`

**本仓库实测：1 分** —— 结构性失衡，是全仓库第二大问题

| 端 | 主源码 | 测试 | 判断 |
| --- | ---: | ---: | --- |
| Java | 111 | **2** | ❌ 1.8%，且只测了 Experiment/Feedback |
| Python | 14 | **0** | ❌ 零测试 |
| 前端 | 83 | 25 spec / 303 项 | ✅ 达到企业水准 |

- ✅ 前端测试是标杆：303 项、10 份门禁、7 项冒烟、10 场景 CDP 回归
- ❌ Java 的 111 个类里，`ChatServiceImpl`（533 行）、`IndexServiceImpl`（730 行）这两个最复杂、最容易出错的类**完全没有测试**
- ❌ 根 `test/` 的 31 个 pytest 文件是**黑盒门禁**（打 HTTP 接口），不是单元测试——它能验证行为对不对，但定位不到是哪一行错了

**这是最值得投入的一项**：给 `ChatServiceImpl` 和 `IndexServiceImpl` 补单测，收益远大于任何重构。

## D8 · 交付与运维 ★★

**核心问题：新人能一条命令跑起来吗？改动能自动验证吗？**

| 分 | 标准 |
| ---: | --- |
| 3 | CI 自动跑 lint+test+build；多环境配置分离；镜像可复现（固定版本）；有回滚方案；有部署文档 |
| 2 | 有 Dockerfile + compose；配置走环境变量；门禁脚本可手工跑 |
| 1 | 能本地跑，部署靠口口相传 |
| 0 | 跑不起来 |

**证据采集**：快照 §8（工程化配置表）

**本仓库实测：2 分**

- ✅ 三个 Dockerfile + `deploy/docker-compose.yml`（含 healthcheck、depends_on 条件）
- ✅ 配置全部走环境变量，密钥用 `${VAR:?required}` 强制校验
- ✅ 门禁脚本齐全（`gate.mjs` 四道、`smoke.mjs`、`regress.mjs`）
- ❌ **无 CI 流水线**——门禁全靠人记得跑
- ❌ 无根 `README.md`（新人不知道从哪进）
- ❌ 无 K8s/Helm（教学项目可接受）

**修法**：加一个 30 行的 GitHub Actions，跑 `npm run gate` + `mvn -q verify` + `pytest test/`。这是投入产出比最高的一项。

## 附：让 LLM 输出更狠的三个提问模板

**模板 A · 找最痛的**
> 按 D1–D8 打分，然后只回答一个问题：如果这个项目明天要上线给 1000 个用户用，最先炸的是哪一处？给出文件路径、触发条件、爆炸半径。

**模板 B · 面试官视角**
> 假设你是面试官，要在 20 分钟内判断作者是否真懂企业级后端。你会挑哪 5 个点追问？每个点指出本仓库的代码位置，并说明为什么这里站不住。

**模板 C · 反事实**
> 假设半年后要加"多租户"能力。以现在的分层，需要改多少个文件？列出会被迫修改的文件清单。改动面越大，说明架构耦合越重。

模板 C 特别有用——**它测的是架构的"可演进性"，而这恰恰是目录结构看不出来的。**
