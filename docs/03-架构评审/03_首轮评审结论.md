## 二、P0 · 不改就会出线上事故

### P0-1 资料越权：任何登录用户可修改、删除他人资料

**证据**

| 位置 | 事实 |
| --- | --- |
| `service/DocumentService.java:21` | `List<DocumentVO> list()` —— **不接收 userId** |
| `service/DocumentService.java:39` | `update(Long documentId, ...)` —— **不接收 userId** |
| `service/DocumentService.java:46` | `delete(Long documentId)` —— **不接收 userId** |
| `controller/KnowledgeController.java:54` | `listDocuments()` 完全没取当前用户 |
| `controller/KnowledgeController.java:84` | `deleteDocument(@PathVariable String id)` 只认 id |
| `model/entity/Document.java:63` | 有 `uploadedBy` 字段，但**只做审计，不做访问控制** |

**对照证据（关键）**：`service/ConversationService.java` 的 5 个方法**全部**带 `userId`（第 21/30/38/51/59 行），会话侧隔离是正确的。

> **同一个仓库里两种做法并存** —— 这说明问题不是"作者不会写租户隔离"，而是"没有统一约束，写哪算哪"。这是架构问题，不是 bug。

**触发条件**：任意用户登录后，把 `DELETE /api/v1/documents/7` 里的 id 改成 8，就能删掉别人的资料。无需任何特殊权限。

**爆炸半径**：全部资料数据。且 `delete` 是软删除，出事后连恢复都要手工改库。

**修法**（按顺序，约 6 个文件）
1. `DocumentService` 三个方法签名加 `Long userId`
2. `DocumentServiceImpl` 里 `list` 加 `where uploadedBy = :userId`，`update`/`delete` 先 `findByIdAndUploadedBy` 校验归属，不匹配抛 `40300`
3. `KnowledgeController` 三个方法补 `@RequestAttribute(ATTR_USER_ID)`
4. **删掉** `KnowledgeController.java:72` 的 `userId == null ? 1L : userId` —— 这是第二个后门，未登录请求会直接落到 user 1 名下
5. 补一个测试：用户 A 建资料 → 用户 B 删 → 断言 403

### P0-2 鉴权是内存后门 token，永不过期

**证据**

| 位置 | 事实 |
| --- | --- |
| `common/interceptor/AuthInterceptor.java:48` | `demoTokens.put("dev-token", 1L)` —— 构造函数里硬塞一个永久有效 token |
| `common/interceptor/AuthInterceptor.java` 类注释 | 自述「只校验头存在且非空，不验签」 |
| `backend/java-api/pom.xml` | **无** `spring-boot-starter-security`，**无** JWT 库 |
| `config/XiaoyiProperties.java:82` | `internalToken = "dev-internal-token"` 硬编码默认值 |
| `apps/web/src/api/modules/auth.ts:13` | 写死 `{ username: 'demo', password: 'demo' }` |

**触发条件**：任何人带 `Authorization: Bearer dev-token` 即可获得 userId=1 的完整权限。这个 token 写在源码里，且在 `docker-compose` 部署后依然生效。

**修法**（二选一，按投入排）
- **低成本**：`AuthInterceptor` 里删掉 `demoTokens.put("dev-token", 1L)`，改为仅接受 `login` 动态签发 + 内存过期时间戳（`Map<String, Entry<Long, Long>>`），并给 `XiaoyiProperties.internalToken` 去掉默认值，强制环境变量注入
- **正解**：引入 `jjwt`，token 带 `exp`/`iat`，`AuthInterceptor` 换成验签 + 过期校验；`internalToken` 改为启动时随机生成并注入 Python 侧

**注意**：教学项目用简化认证**可以接受**，但必须做两件事：① 删掉硬编码后门；② 在文档里显式标注「认证为演示级，不含验签与过期」。现在的状态是"看起来像做了认证"，比"明确不做"更危险。

### P0-3 Python 服务用模块级全局状态存业务数据

**证据**

| 位置 | 事实 |
| --- | --- |
| `backend/ai-api/app/main.py:15-17` | `tasks = {}` / `documents = {}` / `chunks = []` 三个模块级可变全局 |
| `backend/ai-api/app/main.py` | 8 个路由 + 全部业务逻辑 + mock 数据 + SSE 拼装，全在这一个文件 |
| `backend/ai-api/app/services/state.py:1` | `from app.main import tasks, documents, chunks` —— 业务模块反向依赖入口 |
| `backend/ai-api/app/api/__init__.py` | 空包，建了目录但没用 |
| `backend/ai-api/app/core/rag/service.py` | 存在，但 `main.py` 未使用（并行死代码） |

**触发条件**：`uvicorn --workers 4` 启动后，4 个进程各有一份 `tasks`/`chunks`。用户建库请求打到 worker 1，轮询状态打到 worker 2 → 返回「任务不存在」。**当前 `docker-compose` 用单 worker，所以没暴露；一旦上生产多 worker 立刻炸。**

**爆炸半径**：建库、片段浏览、检索全部失效。

**修法**（约 4 个文件，1–2 天）
1. 抽出 `app/services/task_store.py`，用 `Protocol` 定义接口，先实现内存版（单 worker 可用），预留 Redis 版
2. 路由按领域拆到 `app/api/routes/chat.py`、`ingest.py`、`retrieve.py`、`eval.py`
3. `main.py` 只保留 `create_app()` 装配
4. **删除** `services/state.py`（反向依赖的根源）

## 五、做对了什么（同样要给证据）

评审如果只说问题，结论不可信。以下三项确实达到了企业水准：

**1. 契约治理（D2 = 3）**
`docs/api/openapi-public.yaml`（67 KB）+ `openapi-internal.yaml`（29 KB）+ `envelope.schema.json` + `error-codes.md` 四件套齐全，前端用 `openapi-typescript` 生成类型（`npm run gen:api`），统一信封 `{code, message, data, timestamp}`。**多数企业项目做不到这个程度。**

**2. 前端 SSE 与 HTTP 层（超出预期）**
`apps/web/src/api/sse.ts` 手写了完整的 SSE 解析器，处理了：
- 半包（`remainder` 保留）
- 粘包（一次 drain 多帧）
- CRLF/LF/CR 三种分隔符
- `:` 开头的 keep-alive 注释
- **abort 后 `reader.read()` 不 settle 的竞态**（用 `Promise.race` 抢中止信号，第 148–158 行）
- `reader.cancel()` 不 await（第 182 行，注释说明 polyfill 会挂死）

这些是真实线上才会踩的坑。`http.ts` 的 401 清 token + 503 降级广播、非 JSON 错误体兜底也都到位。

**3. 前端测试（D7 的前端部分 = 3）**
25 个 spec / 303 项，配 10 份阶段门禁 + 7 项冒烟 + 10 场景 CDP 回归。这个测试密度高于多数商业项目。

**4. 一个正确示范**
`ConversationService` 的 5 个方法全部带 `userId`——**P0-1 的修法直接照抄它就行**，不需要重新设计。

## 六、反事实推演：加「多租户」要改多少

假设半年后要支持「每个用户只能看到自己的资料和对话」：

**已经就绪**：17 个文件已贯穿 `userId`，会话侧完全隔离。

**需要改的**：

| 层 | 文件 | 改什么 |
| --- | --- | --- |
| 实体 | `Document.java` | `uploadedBy` 改为强约束 + 加索引 |
| 迁移 | 新增 `V7__doc_owner.sql` | 回填历史数据、加 `NOT NULL`、加索引 |
| Service | `DocumentService` + Impl | 3 个方法加 userId 与归属校验 |
| Controller | `KnowledgeController` | 3 个方法补 `@RequestAttribute`，删兜底 |
| Service | `IndexService` + Impl | 建库按租户隔离（索引/manifest 分片） |
| Python | `main.py` 的 `chunks` | 全局列表改为按 `doc_id` 分区 + 租户字段 |
| 前端 | `api/modules/knowledge.ts` | 无改动（靠 token 隐式带租户） |

**约 8 个文件**，其中 6 个是 P0-1 本来就要改的。

**结论**：改动面可控，说明分层本身是健康的。**真正的问题不是耦合重，而是"该统一的约束没统一"**——会话做了租户隔离，资料没做。这类问题的修法不是重构，是补一条规范 + 一个测试。

## 八、这次评审方法本身的复盘

**有效的地方**：
- 快照把 15000 个文件压到 293 行，一次就能喂完
- 强制引用行号，逼出了 P0-1 这种"看目录看不出来"的问题
- 对照 `ConversationService` vs `DocumentService` 找不一致，比逐文件读高效得多

**差点误判的地方**：
- 一开始看 `WebClientConfig` 是空壳，判定「无超时配置」，给了 D6 = 1 分。实际打开 `RealAiServiceClient` 才发现超时和重试都做了，**修正为 2 分**
- 一开始以为 `apps/web/src/mocks/` 会打进生产包，核实后发现 `main.ts:13` 用 `import.meta.env.VITE_USE_MOCK` 守卫 + 动态 import，是正确做法

**教训**：**类名和目录名会骗人，只有打开文件才算数。** 这也是为什么 P1 提示词里必须写死「给不出证据就删掉结论」。
