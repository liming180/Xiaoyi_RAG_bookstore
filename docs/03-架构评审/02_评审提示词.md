# 评审提示词包

> 用法：**复制整段**（含代码块）粘贴到 LLM 会话里，替换 `【】` 中的占位内容。
> 三轮必须按顺序执行——第 2、3 轮依赖第 1 轮的结论。

---

<a id="p1"></a>
## P1 · 架构符合性评审

**目的**：找出「声明的架构」与「实际的代码」之间的差距。不谈改进，只谈事实差。

**需要喂给它的材料**：`snapshot/架构快照.md` + 架构规格文档

```text
你是一位有 15 年经验的后端架构师，正在做技术尽职调查（technical due diligence）。
你的任务不是夸，是找差距。任何没有证据的结论都会被直接删除。

## 材料

【材料 1：架构声明】以下是项目文档中声明的架构设计：
<<<
粘贴 docs/02-重构设计/00_项目架构规格.md 的「三端拓扑」和「架构铁律」章节
>>>

【材料 2：架构快照】以下是从代码库机械提取的事实清单：
<<<
粘贴 docs/03-架构评审/snapshot/架构快照.md 全文
>>>

【材料 3：评审基线】8 个维度，每维 0-3 分：
<<<
粘贴 docs/03-架构评审/01_企业级基线.md 的「评分总表」和 D1-D8 各节
>>>

## 任务

按顺序完成三件事：

### 1. 差距表
把「材料 1 声明的」和「材料 2 实际存在的」逐条对齐，输出表格：

| 声明内容 | 实际状态 | 是否一致 | 证据 |
| --- | --- | --- | --- |

「证据」列必须是 `文件路径:行号` 或快照章节号（如 §9.3）。**给不出证据的行，标注「无法验证」而不是猜测。**

### 2. 逐维度打分
对 D1-D8 每一项给 0-3 分，格式：

**D1 分层与依赖方向：X/3**
- 加分证据：...
- 扣分证据：...
- 与满分差距的具体表现：...

### 3. 三个最严重的问题
只选三个。每个用这个结构：

- **问题**：一句话说清
- **证据**：文件路径:行号
- **触发条件**：什么情况下会真的出事
- **爆炸半径**：影响哪些功能/哪些人
- **修法**：具体到「改哪个文件、拆成什么、先做哪一步」

## 约束（违反即作废）

1. 禁止出现「整体不错」「建议完善」「可以考虑」这类无信息量的表述。
2. 每条结论必须能追溯到材料 2 的章节号或具体文件。
3. 不确定的地方写「需要人工核实：<具体要核实什么>」，不要编。
4. 不要给「加注释」「补充文档」这类不解决结构问题的建议。
5. 总字数控制在 1500 字以内。宁可少说，不要注水。
```

粘贴 P1 的完整输出

## 输出格式

### A. 按「会出事的时间顺序」排列的问题

不要按严重程度排，按「什么时候会咬到你」排：

| 何时会出事 | 问题 | 证据 | 后果 |
| --- | --- | --- | --- |
| 上线第一天 | ... | ... | ... |
| 第一个月 | ... | ... | ... |
| 半年后 | ... | ... | ... |

### B. 三档待办

**P0（不改就会出线上事故）** — 最多 3 条
每条格式：`[文件:行号] 问题 → 改法 → 预估改动面（几个文件/几行）`

**P1（影响可维护性，三个月内必须做）** — 最多 4 条
同样格式。

**P2（锦上添花，可明确不做）** — 最多 3 条
每条必须写「为什么现在不做也安全」。

### C. 一个反事实推演

假设半年后要加「多租户」能力（每个用户只能看到自己的资料和对话）。
以现在的分层，列出**会被迫修改的文件清单**（按路径列），并统计总数。

如果超过 15 个文件，说明架构耦合过重，请在结论里明说。

## 约束

1. P0 必须是真的会导致数据错误、安全漏洞或服务不可用的问题。代码风格问题一律不许进 P0。
2. 每条待办必须给出文件路径和行号。
3. 如果某个问题在 P1 已经提过，这里只需引用「见 P1 第 N 条」，不要重复展开。
4. 明确说出「哪些地方做得比一般项目好」——最多 3 条，同样要给证据。这是为了让结论可信，不是客套。
```

| 维度 | 分 | 证据 | 差距 |

| 优先级 | 问题 | 证据 | 用户感知 | 改动面 |

这个前端如果明天上线给 1000 个用户用，**最可能被投诉的是哪一件事**？

## 约束

1. 不要建议引入新的状态管理库、UI 库、测试框架——现有技术选型已定，只评估「用得对不对」。
2. 不要评论样式细节（颜色、间距），除非影响可用性。
3. 前端已有 25 个 spec / 303 项测试，这是加分项，请在结论里明确承认，不要无视。
4. 每条结论必须指向具体文件。

## 附加提示词 · 架构漂移监控

**用途**：重构前后各跑一次快照，让 LLM 判断架构是变好还是变坏。

```text
以下是同一个项目在重构前后的架构快照 diff：

```diff
【粘贴 git diff docs/03-架构评审/snapshot/架构快照.md 的输出】
```

请判断：
1. 哪些指标变好了？哪些变坏了？逐条列出。
2. 有没有「表面变好、实际变坏」的情况？（例如：文件数减少但其实是大文件合并；测试数增加但都是 getter 测试）
3. 用一句话给这次重构下结论：值得做 / 白做了 / 做了一半。

不要客套。如果 diff 显示没有任何实质改善，直接说「这次重构没有解决任何架构问题」。
```
