第 3 部分 · 三个最严重的问题

问题 1：演示模式认证是后门，生产环境直接失控
- 证据：AuthInterceptor.java:48 硬编码 demoTokens.put("dev-token", 1L)；XiaoyiProperties.java:82 internalToken 有默认值；frontend/src/api/modules/auth.ts:13 写死 { username: 'demo', password: 'demo' }；AuthController.java:54 与 KnowledgeController.java:72 各有一处 userId == null 兜底
- 触发条件：任何人带 Authorization: Bearer dev-token 请求 API；或知道内部 token 的人直接访问 Python 服务
- 爆炸半径：
  · 所有用户数据互通（无租户隔离），A 可删 B 的会话与消息
  · 内部 token 泄露后可绕过 Java 网关直接控制 Python 服务（任意建库、删索引、读所有文档）
  · 硬编码 token 无法撤销、无法追溯、无法限速
- 修法：
  立即：删 AuthInterceptor.java:48；XiaoyiProperties.java:82 去掉默认值，启动时从 XIAOYI_AI_INTERNAL_TOKEN 强制读取（缺失则启动失败）；删两处 userId == null 兜底
  阶段 2：引入 spring-boot-starter-security + jjwt；AuthController.login 签发 JWT（userId + exp + iss）；AuthInterceptor 改用 JwtParser 验签；加 /auth/refresh
  阶段 3：所有 repository 查询加 userId 过滤（findByIdAndUserId），防越权读写

问题 2：Java 核心服务类超长无测试，变更风险无法控制
- 证据：快照 §9.1 IndexServiceImpl.java 730 行、ChatServiceImpl.java 533 行；快照 §7 Java 测试文件 2 个（1.8%），这两个最复杂的类完全没有测试
- 触发条件：需求变更（流式中断、多模态文档、改建库策略）必须改这两个类，但无测试覆盖，每次改动靠人工黑盒验证
- 爆炸半径：
  · ChatServiceImpl 533 行含 SSE 编排、降级、异步落库、事务边界——任一环节出错导致消息丢失、前端卡死、数据不一致
  · IndexServiceImpl 730 行含建库触发、轮询、manifest 比对、状态机——出错导致建库卡死、重复任务、索引不一致
  · 无测试 = 重构成本极高，技术债持续累积
- 修法：
  立即：为 ChatServiceImpl 补单测（MockMvc + Mockito mock AiServiceClient）：测 prepare（mode/k 校验、history 截取、会话自动创建）、测 stream（mock 事件序列，验证透传）、测降级（mock 抛异常，验证 done.degraded=true）、测落库（验证 ChatPersistService 异步调用与 messageId 回填）
  先拆再补：IndexServiceImpl 按职责拆三个 service —— IndexOrchestrationService（rebuild 编排、manifest 比对、状态判定，< 200 行）、IndexTaskService（任务增删查、状态机，< 150 行）、IndexTaskPoller（轮询与重试，< 100 行），每个补单测
  CI 门槛：pom.xml 加 jacoco，service 层覆盖率 ≥ 60%，核心类 ≥ 80%，未达标 CI 失败

问题 3：Python 端无分层且无测试，整个 RAG 链路是黑盒
- 证据：基线 D1（01_企业级基线.md:53）「8 个路由 + 全部业务逻辑 + mock 数据都在 main.py，app/api/ 是空包」；快照 §7「Python 测试文件 0」；快照 §9.4 main.py 有 3 个模块级全局状态（tasks / documents / chunks）
- 触发条件：调整 RAG 流程（加重排、改 RRF 权重、切换向量模型）必须改 main.py；多人协作冲突频繁；无法单测某个组件
- 爆炸半径：
  · 所有 RAG 逻辑耦合，改一处影响全局
  · 模块级全局状态在多 worker 下失控（uvicorn 默认多 worker）
  · 无测试 = RAG 效果回退无法自动发现
  · 无法替换组件（Milvus Lite → Milvus、jieba → 其他分词器），依赖写死在 main.py
- 修法：
  立即（按规格 §6 重构）：新建 app/api/chat.py、knowledge.py、eval.py 迁入 8 个路由；新建 app/services/chat_service.py（pipeline 编排）、ingest_service.py（建库）、eval_service.py（批量评测）；新建 app/core/rag/pipeline.py（改写→检索→重排→生成四阶段接口化）、retriever.py（混合检索抽象基类）；全局状态 tasks/documents/chunks 改 Redis 或 SQLite，或至少用 asyncio.Lock 保护
