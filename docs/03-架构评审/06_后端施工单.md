## 5. H3：一致性与恢复

源码起点：`IndexServiceImpl.java:231` 先查再建；`:255` 事务内调用外部服务；`:436` 全局提升状态；`:451` 删除旧代缓存。`ChatServiceImpl.java:328` 提交异步落库；`:335` 捕获失败后仍发 done。

1. Java 用数据库原子占位保证同一用户最多一个活动重建；幂等键至少含用户、资料版本快照、参数和模型。不能只对 chunkSize/overlap/model 建永久唯一约束，否则相同参数的新资料无法重建。
2. 分短事务持久化任务→事务外提交 Python→短事务保存 externalTaskId；Python 按提交键去重。覆盖“Python 已受理但响应丢失”，避免重试生成孤儿任务。
3. Python 执行任务状态独立存储，不直连 Java 业务库；小规模可用持久化 SQLite+单 worker，明确恢复为续跑或 FAILED。独立多实例需共享状态方案后再开放；Redis/Celery 非本次默认依赖。
4. 建库产物先写新 generation，校验后原子切换；只更新任务实际包含且版本未变的文档。旧代清理在切换之后，重启不丢已发布索引。
5. Java 落库失败或 executor 拒绝时发送明确 error 并结束流，禁止以成功 done 或 Python 假 messageId 掩盖。对客户端断连释放上游连接，测试终态只触发一次。

验收：并发重建只受理一个；超时重试同任务；重启有确定终态；建库期间新上传资料仍为待建；失败不破坏上一代；数据库写入失败不发成功 done。

### 9.1 本机 MySQL 直连模式（三端在本机进程，不涉及 Docker）

`deploy/docker-compose.yml` 是交付形态，但验收不依赖镜像仓库：三端可直接连本机 MySQL 8.0，表结构由 Java 启动时的 Flyway V1–V7 建立，与 compose 内 java-backend 跑的是同一份迁移 SQL。

```powershell
copy deploy\local-mysql.env.example deploy\local-mysql.env   # 填 MYSQL_PASSWORD + 两个密钥
python tools\local_mysql.py prepare                          # 只 CREATE DATABASE IF NOT EXISTS
python tools\local_mysql.py up --timeout 180                 # Python(8000) + Java(8080)，Flyway 建表
python tools\local_mysql.py verify                           # 双账号 + 13 表 + Flyway 全 success
python tools\local_mysql_smoke.py                            # 上传→建库→轮询→A/B 隔离断言
python tools\local_mysql.py down                             # 只停本工具进程，不停 MySQL，不删库
```

实测证据（2026-11-05）：

- 空库从零迁移：`Successfully applied 7 migrations to schema xiaoyi_rag_local_gate, now at version v7 (execution time 00:01.915s)`，13 张表（含 `flyway_schema_history`）。
- `verify` → `pass=true`，`local-a(id=2)` / `local-b(id=3)` 各登录 200，`health={java:200, python:200}`。
- `local_mysql_smoke.py` → `isolation ok A=1 B=0`，`users=['demo','local-a','local-b']`，`PASS`。
- 浏览器双账号（真实 provider）→ G1/G2/G3/G4 全 PASS。
- 根门禁真实 provider 档 → `257 passed, 1 skipped`；mock 档 `J3+J5` → `55 passed`。
- 硬约束与 compose 一致：库名须以 `_gate`/`_test` 结尾、`AUTH_JWT_SECRET` ≥ 32 UTF-8 字节、`INTERNAL_TOKEN` 非空、bootstrap 口令 12–72 字节，缺项即 fail-fast。

### 9.2 Docker 起整套服务 + 宿主机 MySQL（2026-11-06 实测通过，A 项取证拓扑）

```powershell
mysql -u root -p -e "CREATE DATABASE IF NOT EXISTS xiaoyi_rag_local_gate CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;"
python tools\local_mysql_grant_container.py                    # 建 xiaoyi@'%'
cd server-java; mvn -q -DskipTests package; cd ..
cd frontend; npm run build:only; cd ..
$env:MYSQL_USER_FOR_CONTAINER = 'xiaoyi'
docker compose -f deploy/docker-compose.localdb-prebuilt.yml --env-file deploy/local-mysql.env up -d --build
python tools\compose_smoke.py                                  # 走 nginx:8088，报告 test-artifacts/compose-smoke.json
docker compose -f deploy/docker-compose.localdb-prebuilt.yml --env-file deploy/local-mysql.env down
```

### 11.3 验收期修的三处排序缺陷（都由四档对照量出来）

1. **本地词项重排把排序变差**：最初 `LexicalReranker` 丢掉 RRF 分、只按词面覆盖率重排，top-1 从 5/6 掉到 3/6。改成 0.6/0.4 加权 → 4/6，0.85/0.15 → 4/6，都不如不重排。最终定案：降级路径**保序**，词项分只做并列消歧，契约是「不比不降级更差」。

### 11.5 资料编号容量（验收期修的真实缺陷）

`chunk_id` 形如 `D01-C001`，文档号只有两位，因此**一个用户同时最多 99 份资料**。旧实现有两处把这条边界做成「静默损坏」：

1. `_document_no()` 把 `>99` 的编号 clamp 成 99 → 第 100 份起所有资料都编成 `D99-Cxxx`，同一次 upsert 主键重复，Milvus 只回一句 `code=1100 duplicate primary keys are not allowed in the same batch`，任务里只留一句看不出根因的「解析任务失败」。
2. `upsert_document()` 用 `MAX(doc_no)+1` 分配编号，且 Python 从不知道 Java 删过资料 → 编号只增不减，「累计上传过 99 份」就等于永久报废。实测 `local-a` 累计到 122 份后建库直接失败。

现在的做法：

- 编号取**当前最小空闲号**，删掉的号能被复用（只取空号、不重排已有编号：重排会改动并发任务正在用的号）；
- 每次建库前 `reconcile_documents()` 拿请求里的全量资料集对账，回收已删除的资料连同切片；但只回收 `updated_at` **早于本次任务开始时刻**、且不在请求集合里的行 —— 同一用户两次建库时间上重叠时，后一个任务刚登记的资料不能被前一个任务的对账删掉（第一版无条件删，实测把并发任务的资料删了，报「资料 495 尚未登记编号」）；
- 编号查不到时就地补登记，而不是报错 —— 并发建库时另一个任务可能刚回收过这个号；
- 真的满了就抛带动作的错：`资料数已达上限：用户 N 同时最多 99 份（chunk_id 的文档号只有两位）；请先删除不再需要的资料再建库`；
- 写入前自查同批重复 `chunk_id`，报错点名「先出现的 doc 与撞上的 doc」，把定位成本从翻库降到读报错。

对应用例：`test_document_number_over_limit_fails_with_actionable_message`、`test_deleting_documents_frees_doc_numbers_for_new_uploads`、`test_reconcile_keeps_documents_registered_by_a_concurrent_task`、`test_duplicate_chunk_id_in_one_batch_is_reported_by_doc`（`test/A2-rag/test_ingest_pipeline.py`）。

## 12. N1 实验参数真生效（2026-11-08 实施并验收）

报告：`docs/03-架构评审/evidence/backend-gate-N1.json`。需求来源：[05_后端开发提示词_亮点包后端.md](../02-重构设计/05_后端开发提示词_亮点包后端.md) §3。

### 12.1 缺陷：四根轴里三根是装饰

参数实验的界面有四根轴 —— `chunkSize` / `overlap` / `k` / `rerank`（外加 `summary`）。修之前只有 `k` 是真的：`ExperimentServiceImpl.execute(...)` 只把 `params.get("k")` 传给 `evaluations.evaluate(...)`，其余四个键写进 `params_json` 落库后**无人读取**。

后果不是「功能少了」，而是**仪器不准**：报告里两行参数明明不同，`hitRate` / `avgElapsedMs` / `avgSources` 却完全一样。于是「混合检索有没有变好」「分块大小该取多少」这类结论全部建立在同一份向量库上，参数只是标签。这比没有实验功能更糟 —— 没有功能时人不会信，有了假功能人会信。

根因在一层，但穿透了四层：

1. 内部契约 `InternalChatRequest` 是 `additionalProperties: false` 且没有 `options` 字段 → Java 就算想传覆盖项也无处可放；
2. Python 侧 `ChatRequest` 没有 `options` → Pydantic 静默丢弃未知键，即便契约加了也收不到；
3. `ingest.retrieve(...)` 里 hybrid 分支**无条件**调 `self.reranker()`，只看全局 `settings.retrieval_rerank`，没有逐请求覆盖的入口；
4. `chunkSize` / `overlap` 是**建库参数**，片段一旦切好就固化在向量库里 —— 不重建索引，这两个轴在原理上就不可能生效，而 `execute()` 从来没重建过。

### 13.1 缺陷：一个常量冒充推荐，且刷新即丢

## 14. N3 全局摘要卡（2026-11-08 实施并验收）

报告：`docs/03-架构评审/evidence/backend-gate-N3.json`。需求来源：[05_后端开发提示词_亮点包后端.md](../02-重构设计/05_后端开发提示词_亮点包后端.md) §5。

### 14.1 缺陷：summarizing 是个空转状态

修之前 `server-ai/app/services/ingest.py` 的建库流程有 4 个状态（splitting → embedding → summarizing → done），但 `summarizing` 阶段只做了一次 `time.sleep` 式的推进，**没有任何产出**。所谓「全局摘要卡」在契约里不存在，检索里也不存在。用户问「资料库里一共多少份东西」「借阅规则是什么」，系统只能靠某一条切片碰巧命中，答不上就等于答不上。

四层根因：

1. **建库侧没有产出点**：`run_ingest` 里 summarizing 是个占位状态，唯一的真实动作是把任务状态往前推一格。
2. **切片表没有容纳卡片的位置**：`chunk.doc_id` 是 `BIGINT NOT NULL`，「全库摘要」不属于任何一份资料，没有合法的 doc_id 可填。
3. **检索侧没有兜底通道**：`retrieve()` 只做「向量 + BM25 → RRF → rerank」，召回不到就是召回不到，不会去问「有没有一张能代表全库的卡」。
4. **契约没定义**：`IndexManifest` 没有 summary 字段，前端想显示「本次建库生成了几张卡」也无从读起。

### 14.2 分层修法

| 层 | 改动 | 理由 |
|---|---|---|
| Python | 新建 `server-ai/app/core/rag/summarizer.py` | 摘要生成单独成模块：`mock_cards()` 产统计卡（全库共 N 份资料：…）+ 规则卡（挑含数字的条款句），`generate()` 是**同步**实现 |
| Python | `generate()` 走 `complete_sync`，**不用 `asyncio.run`** | 建库跑在 FastAPI `BackgroundTasks` 的线程池里，线程内再开事件循环会撞 `RuntimeError: asyncio.run() cannot be called from a running event loop` |
| Python | mock provider 直出确定性卡片；real provider 异常/解析失败一律 `return []` | **real 档绝不拿确定性卡片冒充模型产出** —— 用户看到「全库共 3 份资料」以为是模型总结的，其实是模板，这比没有卡片更糟 |

### 14.4 验收期踩到的坑

1. **「每个问题都塞概览卡」**：按提示词字面实现后，A3 五条 shape 用例同时红。这不是提示词写错，是提示词把验收标准写成了实现步骤 —— 真正要验收的是「全局问题能答」，不是「每轮都插一张卡」。改判据 + 补反向用例才闭合。
2. **BM25 缓存把统计卡当规则卡**：`kind=summary` 与 `kind=rule` 语料都 1 条，revision 相同 → 缓存 key 撞车。判据是「规则卡的正文里出现了份数」，看起来像摘要生成错了，实际是缓存层。教训：**凡是「两个 scope 语料条数恰好相同」的缓存，revision 就不能单独做 key**。
3. **`asyncio.run` 在线程池里炸**：`summarizer.generate()` 最初写成 async，建库线程里 `asyncio.run(...)` 直接 `RuntimeError`。改成同步 + `provider.complete_sync()`（内部才 `asyncio.run`），且异常一律吞掉返回 `[]` —— 摘要失败不该让整库建不起来。
4. **`mvn verify` 无明细失败**：`spring-boot:repackage BUILD FAILURE` 但不打原因，是运行中的 mock 档 Java 占着 `target/xiaoyi-rag-server-0.1.0-SNAPSHOT.jar`。先停 8080 再跑即可。
5. **两条 J4 断言写于 N3 之前**：`test_chunks_return_contract_shape` 里 `row["docId"] == doc["id"]` 现在只对 `kind=chunk` 成立（卡片是 `__summary__` + `D00-*`）；`test_chunks_filter_by_kind` 里 `kind=rule` 不再是空数组。两条都不是「实现错了」而是「断言过期了」，按新语义改判据而不是放宽断言。

1. **hitRate 的分子漏过滤，算出 2.0**。提示词只说「没补 keywords 的标 scored: false，不计入 hitRate」，照字面只改分母。实现里 passed 还是全部 cases 的通过数，测试中 stub 让没关键词的题也「通过」，hitRate = 2 / 1 = 2.0。**分子分母必须落在同一批题上**：cases.stream().filter(c -> scorable.contains(c.questionId())).count() 后再除 scored。这条不做用例就会静默错，所以 ExperimentParamsTest 的 fixture 故意让没词的题也通过。

| 前端 | **早已建成** | `frontend/src/utils/markdown.ts` 的 `parseMarkdown` 支持标题/表格/有序列表/无序列表/加粗/链接；`AnswerBody.vue` 走白名单渲染，全仓 0 处 `v-html` |
| 后端 | 无接口变更 | 回答正文原样透传，不解析 markdown |
| 提示词 | **缺一条约束** | `server-ai/app/core/rag/prompt.py` 的 `SYSTEM_PROMPT` 五条规则里，没有一条提到表格或列表 |

根因一句话：**前端把渲染能力建好了，但提示词里没让模型用**。模型按「简洁、分点」的旧指令写纯段落，`parseMarkdown` 的表格/列表分支永远走不到——这是一段能跑、有测试、但线上永不触发的能力。

这类缺陷特别难被发现：没有报错、没有 500、页面上文字也读得通。唯一的表现是「回答看起来不如别的产品结构化」，而那通常被归因为模型能力。

### 16.2 修法

| 层 | 改动 | 理由 |
| --- | --- | --- |
| 提示词 | `SYSTEM_PROMPT` 末尾追加第 6 条（前五条一字未改） | 只增不改：防幻觉四条是安全底线，动它们要单独评审 |
| 提示词 | 第 6 条点明「编号写在对应单元格或列表项内，不要单独成行堆在末尾」 | 堆末尾时读者要来回找对应，表格反而比段落难读；写进单元格才让「每个数字都有出处」在结构上成立 |
| 提示词 | 第 6 条点明「不要输出 HTML，不要用图片」 | 前端是白名单渲染，HTML 会以尖括号原样显示。禁在前端比禁在提示词代价高（要引 sanitize 依赖或 v-html） |
| 注释 | `prompt.py` 模块 docstring 记「第 6 条必须与 `markdown.ts` 白名单逐条对齐」 | 提示词放开一种语法、前端不认，用户看到的就是一坨裸露的竖线；两边是隐式契约，得写下来 |
| 前端 / 后端 / 契约 | **零改动** | 能力已在，只是没被调用 |

这条改动的风险面被刻意压到最小：一行提示词 + 一段注释。代价是它治不了「模型不听话」——见 16.4。

### 16.4 三个坑与一个如实说明

1. **只断言「常量里有关键词」挡不住「规则没进 messages」**。第一版 `test_system_prompt_has_format_rule` 只检查 `SYSTEM_PROMPT` 字符串，可 `build_messages` 若不用这个常量，规则写得再对也到不了模型。所以加了 `test_format_rule_reaches_provider` —— 断言 `build_messages()[0]["content"] == SYSTEM_PROMPT`。**提示词类改动的验收点不是「文案对」，是「文案到达了调用方」。**
2. **前端断言写成「至少有一个徽标」等于没断言**。把编号全堆到末尾一行的退化写法照样能过，而那恰好是第 6 条要治的毛病。所以钉死「3 行 × 2 列 = 6 个徽标」，位置错了数量就变。
3. **`AnswerBody` 只上抛 `cite` 事件，引用卡在 `MessageBubble` 里渲染**。第一版用例去 `AnswerBody` 的 DOM 里找 `cite-card-wrap`，报找不到元素。改成断言 `wrapper.emitted('cite')[0][0].docTitle` —— 单测要断言组件自己的契约，不是父组件的产物。
4. **如实说明：真实 provider 下模型不一定每次都输出表格**。提示词没有确定性，自动用例只能钉「约束在、能到达模型、渲染不崩」三件事，钉不住「模型一定会输出表格」。mock provider 的回答也不含 markdown，所以 mock 档跑不出结构化回答的端到端效果——结构化渲染的验证落在前端单测（喂手工构造的 markdown）而不是跨端用例。这条已写进 `backend-gate-N5.json` 的 `knownLimitations`，没有伪装成端到端通过。

### 16.5 未做项（如实记录）

- **没有做「模型输出 HTML」的兜底**：第 6 条禁止 HTML，但模型若仍输出 `<table>`，前端会当纯文本转义显示。这是刻意选择——宁可露出尖括号，也不为这一个场景引入 sanitize 依赖或打开 `v-html` 的口子。
- **表格宽时只有 `overflow-x` 滚动**，没做响应式折叠。
- **没给「什么时候该用表格」加判据**：第 6 条只说「需要对比、枚举或分步骤说明时」。要不要在 Java/Python 侧按问题意图预判并强制格式，属于下一轮的话题。
