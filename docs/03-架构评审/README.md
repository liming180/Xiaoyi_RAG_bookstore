# 怎么让 LLM 评审项目架构

> 面向本仓库（Vue 3 前端 + Spring Boot 网关 + FastAPI AI 服务）的实操手册。
> 目标：让 LLM 给出**可验证、可执行、不注水**的架构评审结论，而不是"整体不错，建议完善注释"。

---

## 一、先搞清楚：直接问 LLM 为什么会失败

把项目丢给 LLM 说"帮我看看架构符不符合企业级"，几乎必然得到三种垃圾输出：

| 失败模式 | 表现 | 根因 |
| --- | --- | --- |
| **假装读过** | 说"你的 service 层设计合理"，但其实它只看了目录名 | 上下文装不下。本仓库光 `frontend/` 就有 14422 个文件，LLM 读到 5% 就溢出，剩下靠猜 |
| **无标准打分** | "整体架构清晰，建议增加单元测试和文档" | 你没给判据。"企业级"不是形容词，是一组可核对的属性 |
| **把能跑当架构好** | 接口全通、测试全绿 → 判定"架构优秀" | 功能正确性和架构质量是正交的两件事 |

**核心结论：LLM 擅长判断，不擅长穷举。**

所以正确分工是：

```
机器  →  穷举事实（确定性、可重复）
人    →  提供标准（什么是"企业级"）
LLM   →  对比判断（事实 vs 标准，输出差距和修法）
```

## 二、三步法

### 第 1 步：生成架构快照（机器做）

LLM 读不完 15000 个文件，但读得完 300 行事实清单。

```bash
python tools/arch_snapshot.py
# → docs/03-架构评审/snapshot/架构快照.md（约 290 行 / 11 KB）
```

快照只陈述事实，不含任何评价：

- 三端规模与语言分布
- Java 分层文件分布（哪层有几个类）
- **28 个对外端点** + **8 个内部端点**的完整清单
- 依赖清单、Flyway 迁移清单
- 测试现状（主源码 vs 测试文件数）
- 工程化配置有无（CI / Docker / K8s / README）
- **反模式机械扫描**：超长文件、import 环、分层越界、模块级全局状态、硬编码凭据

为什么必须是脚本而不是让 LLM 自己数：**可重复**。改完代码重跑，diff 一下就知道架构是变好还是变坏。LLM 每次数出来的结果都不一样。

### 第 2 步：喂标准（人做）

读 [`01_企业级基线.md`](01_企业级基线.md)，8 个维度 × 0–3 分。这份基线的作用是**堵住 LLM 的模糊空间**——每个维度都有明确的"3 分长什么样"，LLM 想给高分就得指出具体证据。

### 第 3 步：分三轮问（LLM 做）

**关键：不要一次问三个问题。** 一次问"架构符不符合 + 后端要不要改 + 前端要不要改"，LLM 会把注意力摊薄，三个问题都答得浅。

分三轮，每轮只问一件事，每轮都要求**引用文件路径和行号**：

| 轮次 | 提示词 | 输入 | 输出 |
| --- | --- | --- | --- |
| 第 1 轮 | [P1 架构符合性](02_评审提示词.md#p1) | 快照 + 架构规格文档 | 声明 vs 实际的差距表 |
| 第 2 轮 | [P2 后端完善度](02_评审提示词.md#p2) | 快照 + P1 结论 + 后端关键文件 | 后端待办（按优先级） |
| 第 3 轮 | [P3 前端完善度](02_评审提示词.md#p3) | 快照 + P1 结论 + 前端关键文件 | 前端待办（按优先级） |

第 2、3 轮必须带上第 1 轮的结论——否则前后端评审会脱离架构判断，变成"代码风格建议"。

## 三、让评审不注水的四个技巧

### 1. 强制引用证据

在提示词里写死这条规则：

> 每条结论必须给出 `文件路径:行号` 或快照章节号。给不出证据的结论直接删掉，不要写"建议优化"。

LLM 一旦被要求给行号，就无法泛泛而谈——它要么真去读，要么承认不知道。

### 2. 用「声明 vs 实际」制造张力

单看代码，LLM 会说"分层挺清楚的"。但同时给它两份材料：

- **声明**：`docs/02-重构设计/00_项目架构规格.md` 说"6 条架构铁律"
- **实际**：快照 §9 说"AuthController 跳过 service 直连 repository"

差距一摆出来，评审立刻有靶子。**架构评审的本质就是找声明和实际的差。**

### 3. 要求给出「影响」而不是「建议」

坏输出：`建议把 IndexServiceImpl 拆分`
好输出：`IndexServiceImpl 730 行，承担分块/嵌入/状态机/轮询四种职责。影响：改分块参数要动嵌入逻辑，回归面覆盖整个建库链路；单测无法隔离。修法：拆 IndexChunkService / IndexEmbedService / IndexTaskStateMachine，先抽状态机（无外部依赖，最好测）。`

差别在于：前者是废话，后者可以直接排期。

### 4. 反向提问：让它找「如果这是面试，会被问倒的地方」

正面问"架构好不好"，LLM 倾向于夸。换个问法：

> 假设你是面试官，要在 20 分钟内判断这个候选人是否真的懂企业级后端。你会挑哪 5 个点追问？每个点指出本仓库对应的代码位置，并说明为什么这里站不住。

这个问法能逼出最尖锐的问题，因为"找茬"比"评价"更容易激发具体性。

## 四、什么时候该重跑

快照是架构的"体检报告"，不是一次性文档。以下时机必须重跑：

- 新增/删除 Controller 或路由（端点数变化）
- 新增 Flyway 迁移
- 引入新依赖（尤其安全、可观测性类）
- 里程碑完成（J5、A2、A3 收尾）
- 重构前后各跑一次，用 `git diff` 看架构指标变化

```bash
python tools/arch_snapshot.py
git diff docs/03-架构评审/snapshot/架构快照.md
```

如果 diff 里"超长文件"变多、"分层越界"变多、"测试文件数"没涨，说明架构在恶化——哪怕功能测试全绿。

## 七、一句话总结

**不要问 LLM「我的架构好不好」，要给它一份 300 行的事实清单、一份 8 维度的打分表，然后问「第 3 维度为什么只能给 1 分，证据在哪，怎么改到 2 分」。**

前者得到安慰，后者得到待办。
