## 3. N1：实验参数真正生效

### 3.1 现状（必须先让 LLM 看清）

- `server-java/src/main/java/com/xiaoyi/rag/service/impl/ExperimentServiceImpl.java:125`：
  `evaluations.evaluate(userId, questions, (Integer) params.get("k"), params);`
  —— 只有 `k` 被当成参数用；`chunkSize`/`overlap`/`rerank`/`summary` 只是 `params` 里的键，随 `params_json` 落库后无人读取。
- `server-java/src/main/java/com/xiaoyi/rag/service/impl/EvalServiceImpl.java:184`：
  `new AiChatRequest(question, List.of(), mode, k, List.of(), options)` —— options 确实发出去了。
- `docs/api/openapi-internal.yaml` 的 `InternalChatRequest`（约 482 行）**没有 `options` 字段**，且 `additionalProperties: false`。
- `server-ai/app/schemas/models.py` 的 `ChatRequest` 只有 `question/history/mode/k/acl`，Pydantic 默认忽略多余字段 → 即使发了也收不到。
- 结论：`k` 是真的（进了 `AiChatRequest.k` → Python `ChatRequest.k` → 检索 top-k），**另外三轴是假的**。

**与提示词的偏差（三处，都有理由）**

1. **重建走新通道 `IndexService.rebuildForExperiment(...)`，不是直接调 `rebuild(...)`**：提示词 §3.2 四.1 要求 `rebuild(...)` 在实验期间回 40902，但实验自己每组都要重建 —— 若走同一个入口，实验的第一组就会被自己的互斥拦住。拆两条通道：`rebuild()` 保留 40902 互斥给用户手动建库，`rebuildForExperiment()` 跳过 40902、保留 40903（同用户已有非终态建库任务）。
2. **`chunkSize` 轴的正确性用 `index_task` 落库记录验收，不用 `/index/status`**：`/index/status` 只报**最近一次成功**任务，三组参数各建一次库、收尾又恢复 180/30，跑完再查只剩 180/30 —— 中间两组的参数在黑盒上根本不可见。用例断言 `index_task` 里同时出现 `(300,40)`、`(400,40)`、`(180,30)` 三条 SUCCEEDED。
3. **`gen_summary` 留给 N3**：提示词把 `InternalParseRequest.gen_summary` 写在 N3 的改动面里（§5），N1 不动它，避免 N1 的门禁混进一个尚未实现的字段。

**踩到的坑（写给下一个会话）**

- **Mockito 装桩会污染调用计数**：`when(mock.rebuildForExperiment(...))` 在装桩时就会真调一次 mock，`rebuilds` 列表凭空多一条，`hasSize(2)` 变成 3。必须写 `doAnswer(...).when(mock).rebuildForExperiment(...)`。
- **`mvn verify` 日志里的 stacktrace 大多是刻意构造的失败分支**：`IndexServiceImplTest.rebuildMarksTaskFailedWhenTriggerFails` 会打印「连续失败 30 次」，`ChatServiceImplTest` 会打印「推送失败」，都是 ERROR 级别的正常输出，判据只看 `Tests run: ... Failures: 0`。

## 9. 反模式清单（发给 LLM 时一并投喂）

```text
【本项目已经踩过、不要重犯的坑】
1. 不要用 flush 换可见性。Milvus flush 一次 8–11 秒，A3 阶段因此把建库拖到 20 秒以上；
   正确做法是写/删都不 flush、读侧 consistency_level="Strong"（见 server-ai/app/core/vector_store/store.py）。
2. 不要在 upsert 循环里把 task_id 当逐行标量写。store.py 的 ROW_SCALARS 排除了 task_id，改动前先看注释。
3. 不要让 mock 比真实后端宽松。createConversation 曾因 mock 收下嵌套 body、真实后端回 400，
   导致 302 个前端用例全绿但线上必挂。改 mock 时要和 Java DTO 对齐。
4. 不要给 InternalRetrieveResult 加字段。它是 additionalProperties: false，diagnostics 只能留进程内。
5. 不要用二次排序覆盖 rerank 服务返回的顺序；分数饱和（极差 < 0.01）时要降级而不是硬排。
6. 不要在文档号上做「压实重排」。最小空闲号 + 只回收早于本任务开始的行，是踩过并发 bug 后的定案。
7. 不要把「未执行」写成 PASS。报告里的未执行项必须单列。
8. 跑根门禁前不清那 20 个 provider 环境变量，会出现 100+ 条假失败（实测 112 errors）。
9. PowerShell 里 git push 因 stderr 报 NativeCommandError 退出码 1 是假失败，
   判据用 git rev-list --left-right --count origin/main...HEAD。
10. mvn verify 若报 repackage 无法 rename jar，先看是不是有残留 java 进程占着 target 里的 jar。
```
