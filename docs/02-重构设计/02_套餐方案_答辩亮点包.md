## 1. 选型结论

**选定五项：A5 全局摘要卡 + B1 追问推荐 + C1 回答反馈闭环 + E3 参数实验管理 + B3 结构化回答**

### 1.1 选型理由

| 维度 | 判断 |
|---|---|
| 依赖 | **零新依赖**：全部落在 v2 架构既有设计内（Milvus Lite / Java MySQL / SSE 契约），不需要 MinIO、Redis、多用户提前上 |
| 周期 | 约 1 周（逐项估计见 §2-§6），贴合"实验项目 + 重构并行"的预算 |
| 演示效果 | A5 直接修复教程两大经典失败案例（统计类/资格类全局问题）；C1/E3 体现"数据驱动调参"的工程方法论——答辩时每一个都有可当场演示的前后对比 |
| 架构兼容 | 不改里程碑、不动分层铁律；只做**契约增量**（新增字段/接口），SSE 协议向后兼容 |
| 成长性 | 套餐二/三均是在本套餐之上做加法（升级路径见 §7） |

## 2. B3 结构化回答（先做：其余功能的展示底座）

### 2.1 功能定义
回答支持 markdown 结构化输出：分点、小标题、**表格**（如"各资料借阅规则对比"）。现状回答是纯文本气泡，信息密度低。

### 2.2 设计

| 层 | 设计 |
|---|---|
| Python | 防幻觉提示词（Prompt-1 增量）：追加输出格式约束——"适合用表格/分点呈现时，用 markdown 表格或有序列表组织答案，引用编号 `[Dxx-Cxxx]` 保持在表格单元格/列表项内"。不加独立 LLM 调用，零额外成本 |
| 契约 | 无接口变更（`token` 事件内容本身就是增量文本，前端按 markdown 渲染即可） |
| 前端 | `StreamingText` 组件：流式期间按纯文本累积，`done` 后按 markdown 渲染（或边流边渲染，需容错未闭合表格）；**渲染白名单**：仅允许标题/列表/表格/加粗/链接（链接需 rel=noopener 且仅 http/https），禁 img/script/on* 属性——防检索内容携带恶意标签（呼应教程 §10 注入防御） |
| 前端 | 表格样式沿用设计令牌 U04；表格横向滚动适配窄屏 |

### 2.3 验收标准
1. 提问"对比 01-03 号资料的借阅规则" → 回答含 markdown 表格且每格带来源编号；
2. 引用徽标在表格内仍可点击弹出引用卡；
3. 构造含 `<img onerror>` 的资料片段入库 → 前端渲染不执行（安全验收）。

### 2.4 工作量
Python 0.5 天 / 前端 1 天 / 联调 0.5 天 ≈ **2 天**

## 3. A5 全局摘要卡（本套餐灵魂）

### 3.1 功能定义与用户故事
教程 §11.1 两大失败案例的工程解法：**"黑猫白猫比例"**（Top-K 抽样必然片面）与 **"优惠资格"**（全称+否定规则不存在于任何单条工单）。解法 = 离线让 LLM 通读全库，预生成两类"摘要卡"与普通片段一起入库：
- **统计卡**：全库量化事实（"共 6 份资料；活动 X 场；开放时段…"）；
- **规则卡**：跨文档归纳的资格/边界规则（"哪些事能做、哪些明确不能做"）。

用户故事：*"会员问读书会全年办了多少场活动、每月频率如何"——现状系统只能抽查 3 个片段瞎算；有统计卡后第一条命中的就是准确汇总。*

### 3.2 设计

| 层 | 设计 |
|---|---|
| Python 离线 | ingest 管线末尾新增**摘要生成阶段**：①按文档聚合全文（6 份 md 体量小，可一次通读）；②两次 LLM 调用分别产出统计卡、规则卡（输出结构化 JSON：`kind/title/content/依据文档列表`）；③作为特殊 chunk 入 Milvus Lite，chunk 元数据加 `kind: "summary"\|"rule"`（普通片段 `kind="chunk"`）；④写 manifest（摘要版本、生成模型、源文档集合 SHA） |
| Python 在线 | 检索**同池竞争、不特殊加权**（摘要卡本身就是高信息密度文本，向量+BM25 自然命中）；top-k 截断时保证 `kind=summary/rule` 命中至少保留一条（如融合结果前 k 无摘要卡则用最优摘要卡替换末位——简单可靠的兜底） |
| 契约 | citations 增量字段 `kind`（chunk/summary/rule）；SSE 无变更；`/internal/v1/documents/parse` 请求增 `genSummary: bool`（默认 true），`/internal/v1/ingest/{task_id}` 进度阶段枚举增加 `summarizing` |
| Java | index_task.stage 透传新阶段；建库面板进度文案加"正在生成全局摘要…"；document 表**不新增字段**（摘要卡归属整个知识库，manifest 承载其版本） |
| 前端 | 引用卡上摘要卡显示"🌐 全局汇总"徽标区分于普通片段；知识库页片段浏览按 kind 过滤查看全部摘要卡 |

### 3.3 成本控制
6 份 md 全文约数千字，一次通读 + 两次结构化输出 ≈ 一次普通问答的成本；**仅在重建时发生**，不进在线链路。

### 3.4 验收标准
1. 提问 T 系新增"读书会活动整体情况统计类"问题 → 命中统计卡，数字与资料一致（对照：M4 基线同问题答错或漂移）；
2. 提问资格边界类问题（如"未成年能借书吗"——若资料有据）→ 命中规则卡，答案稳定不随 k 抖动；
3. 摘要卡引用可点击查看卡片全文与依据文档列表；
4. 改动任一资料后重建 → 摘要卡重新生成且 manifest 版本更新。

### 3.5 工作量
Python 1.5 天 / Java 0.5 天 / 前端 0.5 天 ≈ **2.5 天**

## 4. B1 追问推荐

### 4.1 功能定义
每次回答完成后，自动给出 3 个与当前话题相关的追问建议（可点击 chips），把"单轮问答"变成"有来有回的探索"。

### 4.2 设计

| 层 | 设计 |
|---|---|
| Python | 生成完成后追加一次低成本调用（小 max_tokens，prompt：基于本轮问答 + 知识库主题，产出 3 个**资料里有据可答**的追问；要求 JSON 数组输出，失败静默降级为空数组）；**与主回答串行**（需要回答完成后才知道问什么），预算 ~1s |
| 契约 | SSE `done` 事件扩展：`suggestions: string[]`（0-3 条）；对外 `/api/v1/chat/stream` 透传，无新接口 |
| 前端 | 回答气泡底部渲染追问 chips（distinct 样式，与示例问题 chips 区分）；点击 = 以该文本发起提问（自动填充并发送）；会话切换后 chips 随消息保留 |
| Java | 纯透传；落库时 suggestions 存入 message（retrieval_trace_json 旁新增建议字段或并入扩展 JSON） |

### 4.3 验收标准
1. 正常问答后 chips 出现且 ≤3 条；点击 chip 直接发出该问题并得到带引用回答；
2. 拔掉 LLM 降级/超时 → chips 不出现、主回答不受影响（失败静默）；
3. done 事件不含 suggestions 字段时前端不报错（向后兼容）。

### 4.4 工作量
Python 0.5 天 / Java 0.5 天 / 前端 1 天 ≈ **2 天**

## 5. C1 回答反馈闭环

### 5.1 功能定义
每条助手回答可 👍/👎（可附原因标签：答错/没找到/来源不符/其他）；**👎 自动进入 badcase 候选池**，成为 E3 评测实验的素材——让评测集随着真实使用滚雪球。

### 5.2 设计

| 层 | 设计 |
|---|---|
| Java | 新表 `message_feedback(id, message_id, session_id, rating(up/down), tags, comment, created_at)`（一条消息一条，重复提交=覆盖）；新接口 `POST /api/v1/messages/{id}/feedback`、`GET /api/v1/feedback/summary`（按标签/日期聚合） |
| 闭环逻辑 | 👎 的消息落库时自动复制"问题+检索轨迹+回答"到 `eval_run` 的候选题池（新表 `eval_candidate(id, question, source=feedback, status=pending/accepted, created_at)`）；E3 实验创建时可勾选候选题入实验问题集，accepted 后进正式评测集 |
| Python | 无变更（badcase 的检索复现走已有 `/internal/v1/retrieve` + eval/batch） |
| 前端 | 助手气泡右下角 👍/👎 图标（hover 显示，点击后态持久）；提交后 toast"已记录，将用于改进评测"；评测页新增"候选题池"标签页（pending 列表 → 勾选纳入实验） |

### 5.3 验收标准
1. 对某回答点 👎 + 标签"答错" → 候选题池出现该问题（含轨迹）；
2. 候选题纳入 E3 实验后可作为问题集成员跑批量评测；
3. 同一消息重复反馈只保留最新；`/api/v1/feedback/summary` 聚合正确。

### 5.4 工作量
Java 1.5 天 / 前端 1 天 ≈ **2.5 天**

## 6. E3 参数实验管理

### 6.1 功能定义
把"调参凭感觉"变"调参看数据"：一键用**不同参数组合**（chunk_size / overlap / k / rerank 开关 / 摘要卡开关）×（问题集）跑批量评测，自动生成对比报告。这是 M5 效果基线的**操作台**。

### 6.2 设计

| 层 | 设计 |
|---|---|
| 概念模型 | 实验（experiment）= N 个参数组 × 1 个问题集；每组跑一遍 eval/batch → 每组一组指标（命中率/组级通过率 + 耗时/token 成本） |
| Java | 新表 `eval_experiment(id, name, param_matrix_json, question_set_ref, status, created_at, finished_at)` + `eval_experiment_run(id, experiment_id, params_json, metrics_json, raw_run_ref, elapsed_ms)`；接口：`POST /api/v1/eval/experiments`（创建）、`GET /api/v1/eval/experiments/{id}`（进度+各组指标）、`GET /api/v1/eval/experiments/{id}/report`（对比表 CSV/JSON） |
| 编排 | Java 串行调度各组：改参数 → 调 `/internal/v1/documents/parse`（重建）→ 等完成 → 调 `/internal/v1/eval/batch` → 收指标 → 下一组；**注意每次重建覆盖同一向量库**，因此实验必须串行且期间禁用用户提问（前端置"实验进行中"横幅）——这是本功能唯一的架构约束 |
| Python | 无新接口：参数经 parse 请求体传入即可（chunk_size/overlap 已支持）；rerank/摘要卡开关作为 parse/chat 参数增量（`enable_rerank`、`enable_summary`，默认 true） |
| 前端 | 评测页新增"实验"标签：矩阵配置器（勾选要对比的参数与取值）→ 进度 → 对比结果表（行=参数组，列=指标，最优行高亮）→ 导出 CSV |

### 6.3 验收标准
1. 创建 2 组实验（如 k=3 vs k=5）→ 串行执行完成，对比表指标正确、可导出；
2. 实验期间用户发起提问 → 前端横幅提示且后端返回 409（防脏读向量库）；
3. 实验结束后向量库自动恢复到"推荐参数"状态（实验最后一组后重建回默认参数）。

### 6.4 工作量
Java 2 天 / Python 0.5 天 / 前端 1.5 天 ≈ **4 天**（本套餐最大单项）

## 7. 实施顺序、里程碑落位与升级路径

### 7.1 依赖与顺序（共约 13 人天）

```
B3 结构化回答 (2d)          ← 底座：A5 的卡片、B1 的 chips 都受益于 markdown 渲染
   ↓
A5 全局摘要卡 (2.5d)        ← 灵魂功能，依赖离线管道稳定（M2 已就绪）
   ↓ （A5 与 B1 可并行）
B1 追问推荐 (2d)
C1 反馈闭环 (2.5d)
   ↓ （C1 产出候选题，喂给 E3）
E3 参数实验管理 (4d)        ← 收尾：正好用 C1 的 badcase 验证第一轮实验
```

### 7.2 里程碑落位

- 插在 **M4 验收后、M5 开工前**，命名 **M4.5 答辩亮点包**；
- E3 完成即自然过渡到 M5：M5 的"混合检索+重排+查询改写"改造，就用 E3 的实验框架跑 before/after 对比——**本套餐直接成为 M5 的测量仪器**；
- 01_功能扩展清单 §8 套餐一处挂链本文档。

### 7.3 升级路径（本套餐 → 套餐二/三的预留）

| 预留点 | 现在的做法 | 将来长成 |
|---|---|---|
| `eval_candidate.source` 字段 | 现在只有 `feedback` | 套餐三的 D3 荐书审核可复用同一审核流 |
| 摘要卡 `kind` 枚举 | summary/rule 两种 | 套餐二 A2 多知识库：每库各自摘要；D4 新成员引导 = 规则卡的产品化视图 |
| 实验 param_matrix_json | chunk/k/rerank/summary 四参数 | 套餐二接入多 embedding 模型对比（加一维即可） |
| 反馈 tags | 自由标签 | 套餐三 C3 多用户后，反馈按用户聚合做个性化 |
| D1 活动日历 | 不做任何预留（勿过度设计） | 独立 ActivityService，不依赖本套餐任何结构 |

### 7.4 明确不做（本套餐边界）

- 不引入 Redis/MinIO/多用户/LangGraph；
- E3 实验不做并行执行（串行 + 提问互斥已够用）；
- A5 摘要卡不做增量更新（重建即全量重生成，体量小、成本低，增量是伪需求）。
