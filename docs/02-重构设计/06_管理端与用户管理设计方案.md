# 06 · 管理端与用户管理设计方案

> 状态：**已实施并验收（2026-11-10）**
> 版本：v1.2（实施后回填实测偏差）
> 需求来源：① 前端区分管理端与用户端，管理端仅一个 `admin` 账号；② 管理端新增用户管理功能，负责用户账号的增、改、删（对标市面管理后台的标准用户管理）。

## 1. 背景与目标

### 1.1 背景

本系统（星河读书会 · 小忆 RAG 问答）当前只有**单层登录**：任何账号登录后进入同一套界面（对话 / 知识库 / 评测），账号之间只有**数据隔离**（H2 已完成：会话、资料、评测、实验、缓存全链路按 `userId` 隔离），没有**功能分层**——不存在「管理端」概念，也没有任何入口能创建、修改或删除用户账号。账号只能通过环境变量 bootstrap（`AuthAccountBootstrap.java`）在服务启动时创建，运维上每加一个人就得改环境变量重启服务。

### 1.2 需求 → 目标

| # | 需求原文 | 拆解后的目标 | 验收口径 |
| --- | --- | --- | --- |
| 1 | 前端区分管理端和用户端，管理端只有一个名为 admin | ① 角色字段落地为 `ADMIN`/`USER` 双值，ADMIN 全系统唯一且用户名固定 `admin`；② 前端在**同一个 SPA** 内按角色分出管理端分区（`/admin/**`）与用户端分区（`/chat /knowledge /eval`）；③ 登录后按角色分流，USER 无法进入管理端（前端拦截 + 后端 403 双保险） | admin 登录落管理端；普通用户登录落对话页；用户直输 `/admin/users` 被弹回对话页；用 USER 的 token 直调 `/api/v1/admin/**` 得 403 |
| 2 | 管理端新增用户管理功能，负责增改删用户账号 | 管理端提供标准用户管理页：分页列表 + 关键字搜索 + 新建 / 编辑 / 重置密码 / 删除（软删） + 操作审计 | 全部操作走 `/api/v1/admin/users` 五条接口；每次操作写 `audit_log`；删除是软删，该账号立即无法登录，其历史数据保留 |

### 1.3 非目标（明确不做）

- **不做**注册（对外任何注册端点）、邮箱验证、找回密码；
- **不做**多管理员、角色编辑、细粒度权限（RBAC 菜单权限树）——ADMIN 唯一，`role` 只在 `ADMIN` 与 `USER` 两个值之间取值，管理端**不提供**把任何账号改成 ADMIN 的入口；
- **不做**登录名修改（username 是登录标识与 `uploaded_by`、审计归属的锚点，保持只读；改展示名请用 displayName）；
- **不做**第二个前端工程或独立构建产物——管理端是同一 SPA 内的路由分区；
- **不做**账号「禁用」状态（disable）——删除即软删，语义已覆盖「禁用 + 保留数据」，避免引入第三个状态。

> **关键缺口（本设计要补的）**：JWT 不带角色、拦截器不判角色、bootstrap 不设 ADMIN、前端无管理端路由。四件事合起来 = 「有 role 列但全链路没接」。

### 2.1 引用现状的三个设计前提

1. **role 是既有列**：本设计不加 role 相关新表、不动 V1–V10 迁移，只加一个 V11 前向迁移补字段（§6）。
2. **管理端 API 是全新路径前缀 `/api/v1/admin/**`**：不与现有 29 条契约纠缠；现有 29 条的行为、路径、错误码一字不动。
3. **用户端三页 + AppShell 布局零改动**：只动导航数据源（加一个条件项）与路由表（加记录），保证既有 316 项前端测试与后端门禁不受冲击。

## 3. 角色与账号模型

### 3.1 角色取值与不变量

`user.role` 只有 `ADMIN` / `USER` 两个值（大小写敏感；实体 `@PrePersist` 默认 USER，与现状一致）。三条不变量，写进代码与测试：

- **INV-1 唯一 admin**：全库 `role='ADMIN'` 的行**恒等于 1**，且 username 恒为 `admin`。由三道闸保证：
  1. V11 迁移把主 bootstrap 账号升 ADMIN（§6.2）；
  2. `UserService.create()` 只允许创建 USER——创建请求 schema 无 `role` 属性（`additionalProperties: false` 下多传即 40001），service 层再强制 `role=USER`；
  3. 后端测试断言任何创建/更新路径都不产生第二个 ADMIN。
- **INV-2 admin 不可自我毁灭**：admin 不能删除自己、不能编辑自己的账号行、不能重置自己的密码（防止唯一管理员自锁系统）。`PUT /admin/users/{id}`、`PUT /admin/users/{id}/password`、`DELETE /admin/users/{id}` 对 `id == 当前 admin.id` 一律 40906。
- **INV-3 软删即失效**：`deleted=1` 的账号**立即**无法登录（登录查询过滤 deleted）。已签发 token 不主动吊销——`AdminInterceptor` 每次请求查库校验 role 且排除 deleted，所以存量 token 对**管理端**立即失效；对**用户端**三页，登录是签发 token 的唯一入口，删号后无法再签新 token，存量 token 自然过期（TTL 86400s）。残余风险：被删用户 TTL 内的存量 token 仍能调用用户端 29 条接口直到过期。**接受该风险**（内网演示系统，数据仍按 userId 隔离，被删用户的 token 只能操作他自己的数据）；要即时全端失效需追加 token 黑名单，列入 §10.3 后续项，本设计不引入。

### 3.2 账号生命周期

```
创建（管理端表单 / V11+Bootstrap 升级 admin）──► ACTIVE（可登录）
   ├─ 编辑（displayName）──────► 仍 ACTIVE
   ├─ 重置密码（新哈希覆盖）───► 仍 ACTIVE
   └─ 删除（软删 deleted=1）───► 不能登录；不能被编辑/重置/再删（按 40409 处理）；列表默认不显示
```

无恢复入口：username 唯一键在软删行上仍占用，**同一 username 不能被重新创建**。这是有意的——username 是审计与数据归属（`uploaded_by`、会话归属）的锚点，复用会造成历史数据串号；确需重建同名账号属运维操作（前向迁移处理），不进产品功能。

### 3.3 admin 账号的确立方式

- 部署时设置 `AUTH_BOOTSTRAP_USERNAME=admin`（次账号 `AUTH_SECONDARY_BOOTSTRAP_USERNAME` 保持普通用户，例如 H2 隔离测试用的 B 账号）。
- V11 迁移 + `AuthAccountBootstrap` 升级逻辑（§6.3）：启动时若主 bootstrap 账号存在且 role ≠ ADMIN，则幂等升级为 ADMIN。
- 代码里不留写死的 `admin` 字符串作为业务逻辑依据——「管理端只有一个账号」由 INV-1 三道闸保证，`admin` 只是部署约定的用户名；V11 的 UPDATE 语句按 `username='admin'` 匹配只是迁移期的一次性数据修正，应用层兜底按环境变量名匹配。

### 4.3 路由表与守卫

路由表追加（`frontend/src/app/router/index.ts`）：

```ts
{
  path: '/admin',
  component: () => import('@/app/layout/AdminShell.vue'),
  meta: { requiresAdmin: true },
  children: [
    { path: '', redirect: { name: 'admin-users' } },
    {
      path: 'users',
      name: 'admin-users',
      component: () => import('@/features/admin/views/AdminUserListView.vue'),
      meta: { title: '用户管理' },
    },
  ],
},
```

通配路由的 redirect 从静态 `'/chat'` 改为动态 `() => (isAdmin() ? '/admin/users' : '/chat')`。

守卫扩展（`resolveNavigation` 保持向后兼容，在 `router.beforeEach` 里串一条 admin 判定）：

```ts
// adminGuard.ts —— 纯判定层，可单测（仿 guard.ts 的模式）
export function resolveAdminNavigation(
  to: Pick<RouteLocationNormalized, 'meta'>,
  hasToken: boolean,
  isAdmin: boolean,
): GuardDecision {
  if (to.meta.requiresAdmin === true && (!hasToken || !isAdmin)) {
    return { name: 'chat' }; // 未登录或非 admin 一律回对话页
  }
  return true;
}
```

角色来源：登录响应 `user.role`（契约见 §5.6）由 `LoginView` 存入 `localStorage['xiaoyi.role']`，`fetchProfile()` 刷新时同步覆盖。理由：role 属于登录态，随 token 生命周期一起失效，比独立请求轻；`adminGuard` 读 token+role 双值判定，`isAdmin = role === 'ADMIN'`。

### 4.4 登录分流与角色透传

`LoginView` 登录成功后的跳转（现状是 `safeRedirect(query.redirect) ?? '/chat'`）改为：

```
有 redirect query → safeRedirect 后直达
无 redirect：role === 'ADMIN' → /admin/users；否则 → /chat
```

**用户端导航隐藏管理端入口**：`AppTopbar` / `AppSidebar` 的管理端入口 `v-if="isAdmin"`，USER 看不到；即使手输 URL，§4.3 守卫 + §5.4 后端 403 双保险兜底。

- 全部使用现有 Element Plus 组件（`el-table` / `el-dialog` / `el-form` / `el-pagination` / `el-message` / `el-popconfirm`），**不引入**新 UI 库、图标库或动效库（遵守「不为特效更换技术栈」约束）。

## 5. API 契约（契约先行）

### 5.1 契约变更原则

- 契约唯一源头仍是 `docs/api/openapi-public.yaml`：新增 5 条路径与 2 个 schema（`AdminUserItem`、`AdminUserCreateRequest` 等，详见 §5.3）；现有 29 条契约的路径、参数、响应、错误码**一字不改**。
- `UserInfo` 契约**扩一个字段** `role`（§5.6）。为通过 `check:contract` 漂移门禁，`api.d.ts` 的 `UserInfo` 同步加 `role: 'ADMIN' | 'USER'`，然后 `npm run gen:api` 重新生成 `api.generated.ts`。
- 新接口全部挂 `/api/v1/admin/**`，全部要求 role=ADMIN（§5.4）。

### 5.2 新增端点速览

| # | 方法 | 路径 | 用途 | 成功 data | 业务错误码（均叠加 40100/50000 兜底） |
| --- | --- | --- | --- | --- | --- |
| 1 | GET | `/api/v1/admin/users` | 分页列表 + 关键字搜索 | `Page<AdminUserItem>` | 40001、40101 |
| 2 | POST | `/api/v1/admin/users` | 新建用户（只能建 USER） | `AdminUserItem` | 40001、40101、40905 |
| 3 | PUT | `/api/v1/admin/users/{id}` | 编辑显示名（不含密码） | `AdminUserItem` | 40001、40101、40409、40906 |
| 4 | PUT | `/api/v1/admin/users/{id}/password` | 重置密码（独立端点，便于审计与「只改密码」场景） | `AdminUserItem` | 40001、40101、40409、40906 |
| 5 | DELETE | `/api/v1/admin/users/{id}` | 删除（软删） | `null` | 40001、40101、40409、40906 |

### 5.3 逐条契约

#### 5.3.1 GET /api/v1/admin/users

查询参数：`page`（默认 1，≥1）、`size`（默认 20，1–100）、`keyword`（可选，对 username 前缀匹配 + displayName 包含匹配，SQL `LIKE` 参数化）、`includeDeleted`（可选，默认 false；true 时结果包含软删行，仅排障用）。

响应 `data` 为 `Page<AdminUserItem>`，复用现有分页信封形状 `{ items, total, page, size }`。

`AdminUserItem` schema（新增，写进 openapi-public.yaml 时用标准 YAML 语法）：

```
AdminUserItem:
  type: object
  required: [id, username, displayName, role, deleted, createdAt]
  additionalProperties: false
  properties:
    id:          integer ≥1          # 数据库自增主键
    username:    string 1..64
    displayName: string | null       # NULL 时前端回退显示 username
    role:        enum [ADMIN, USER]
    deleted:     boolean
    createdAt:   integer             # Unix 秒，与全站时间戳约定一致
```

字段语义：

- `role` 恒为 `USER`，除 admin 行恒为 `ADMIN`（INV-1）。
- 列表默认只回 `deleted=false` 的行；admin 行始终显示（只读）。
- 排序：`createdAt` 升序（id 升序同序），admin 行天然在首位；与市面后台「按创建顺序」的直觉一致。

#### 5.3.2 POST /api/v1/admin/users

请求体 `AdminUserCreateRequest`：

```
{ username, password, displayName? }
```

- `username`：1–64 字符，`^[a-zA-Z0-9_]+$`，唯一（含软删行占用，§3.2）。
- `password`：12–72 UTF-8 字节（与 `AuthAccountBootstrap` 现行约束一致，见 `AuthAccountBootstrap.java:41-48`）。不做字符类强制；表单侧提示「建议包含字母、数字、符号」。
- `displayName`：可选，≤64 字符；空串存 NULL。
- **不接受 `role` 字段**：请求 schema `additionalProperties: false` 且无 role 属性，传了就 40001——INV-1 的第二道闸。

#### 5.3.3 PUT /api/v1/admin/users/{id}

路径参数 `id`。请求体 `{ displayName }`（字段必填，可空串 → 存 NULL）。**只改显示名，不含密码**——密码走独立端点（§5.3.4），各自留审计痕迹。对 admin 自己的行（id = 当前 ADMIN id）返回 40906「不能对管理员账号执行该操作」（INV-2）。

admin 行在列表中**只读展示**（无操作按钮），让 admin 看到自己是谁，符合市面后台惯例。

#### 5.3.4 PUT /api/v1/admin/users/{id}/password

请求体 `{ newPassword }`，规则同 §5.3.2 的 password。对 admin 自己 → 40906。成功回更新后的 `AdminUserItem`（角色、用户名不变）。

#### 5.3.5 DELETE /api/v1/admin/users/{id}

软删（`deleted=1`）。对 admin 自己 → 前端按钮隐藏 + 后端 40906 双保险（INV-2）。成功回 `{code: 0, data: null}`。

### 5.4 鉴权设计：两级拦截器

```
请求 → AuthInterceptor（验 JWT 签名，取 userId）→ AdminInterceptor（查库判 role）→ Controller
```

- `AuthInterceptor` 现状**保留不动**（挂 `/api/v1/**`，放行 login/health）。
- 新增 `AdminInterceptor`，只挂 `/api/v1/admin/**`：
  1. 从 request 属性取 `ATTR_USER_ID`（AuthInterceptor 已放入；admin 路径不可能没有——AuthInterceptor 先行拦下无 token 请求，401 语义不变）；
  2. 查库 `SELECT role, deleted FROM user WHERE id = ?`（主键点查，只取两列，管理操作低频，成本可忽略）；
  3. `role ≠ 'ADMIN'` 或 `deleted = 1` → HTTP 403 / `40101「无权访问该资源」`（复用 40101 现有语义「已认证但无权限」，对齐 error-codes.md §2 的「403 ↔ 401xx」映射，不改 40101 文案）；
  4. 通过则放行，Controller 直接用 `ATTR_USER_ID` 作为操作者 id 写审计。
- 即时失效性质：admin 密码被重置或账号被删后，**旧 token 对管理端立即失效**（每次请求查库）；这是用「管理端 5 条接口的查库成本」换「即时收权」，值得。
- **现状缺口记录**：`TokenService.verify()` 只解 token 不查库，用户端 29 条接口维持现状不变（不在本设计范围）。

`WebMvcConfig` 变更（追加一段注册，现有注册行不动）：

```java
registry.addInterceptor(adminInterceptor)
        .addPathPatterns("/api/v1/admin/**");
```

### 5.5 service 层不变量（UserService，新建）

`UserService` 持有全部业务不变量，Controller 只做参数透传：

- `create(username, password, displayName)`：username 唯一性检查（含软删行）→ 冲突 40905；bcrypt(12) 哈希入库；强制 `role=USER`；写 audit_log（`admin.user.create`）。
- `update(id, displayName)`：目标存在且未删，否则 40409；目标是自己 → 40906；更新；audit（`admin.user.update`）。
- `updatePassword(id, newPassword)`：同上存在性/自检 + bcrypt 重哈希；audit（`admin.user.reset-password`）。
- `delete(id)`：存在且未删，否则 40409；是自己 → 40906；软删置位；audit（`admin.user.delete`）。
- `list(page, size, keyword, includeDeleted)`：分页 + 过滤，纯读不写审计。

## 7. 安全与审计

### 7.1 密码与凭证

- bcrypt cost 12（与 `AuthService` / `AuthAccountBootstrap` 现行一致），`UserService` 用同一 `BCryptPasswordEncoder(12)` 配置。
- 任何接口**不回哈希**：`AdminUserItem` 无 password_hash 字段（additionalProperties: false）。
- 密码 12–72 UTF-8 字节；服务端按字节长度硬校验，超界 40001「参数不合法」；表单侧提示强度建议。
- **不做**密码历史、复杂度强制、登录失败锁定——内网演示系统，超出需求范围（失败锁定列入 §10.3）。

### 7.2 防自锁与防越权

| 风险 | 防线 |
| --- | --- |
| admin 删/改自己导致唯一管理员自锁 | INV-2：PUT/DELETE/password 对自身 id 一律 40906；前端 admin 行无操作按钮 |
| USER token 调管理端接口 | AdminInterceptor 查库判 role，非 ADMIN 403/40101 |
| 创建第二个 ADMIN | create 请求 schema 无 role 属性（additionalProperties: false → 40001）；service 强制 role=USER |
| 删号后旧 token 残余权限 | 管理端：查库立即失效（§5.4）；用户端：自然过期（§3.1 INV-3 残余风险声明） |
| `//evil.com` 站外跳转 | 复用现有 `safeRedirect`（`guard.ts:43-48`），不动 |

### 7.3 审计日志

`audit_log` 表 V1 已建（`V1__init.sql:101-110`），本次第一次真正写入：

| 字段 | 取值 |
| --- | --- |
| `user_id` | 当前 admin 的 id |
| `action` | `admin.user.create` / `admin.user.update` / `admin.user.reset-password` / `admin.user.delete` |
| `target` | `user:{目标id}` |
| `detail_json` | 变更字段快照；**不含密码明文/哈希**——password 类字段只记 `{"changed": true}` |
| `created_at` | Unix 秒 |

### 7.4 审计查询页（已实现）

> 本节是 §7.3 的配套读入口。写入仍只在 `UserService` 的业务动作里发生，查询侧**完全只读**。

**后端**

| 类型 | 文件 | 说明 |
| --- | --- | --- |
| 仓储 | `AuditLogRepository.search()` | `(:action is null or …)` + `(:operatorId is null or …)` + `(:keyword is null or …)`，`order by id desc` |
| 服务 | `AuditService` | 分页夹取（1–100）、空过滤转 null、操作者名批量解析 |

| 控制器 | `AdminAuditController` | `GET /api/v1/admin/audit-logs`、`GET …/actions` |

三个设计取舍：

1. **过滤条件必须「空转 null」**：JPQL 写的是 `(:action is null or a.action = :action)`，若把空串直接传进去，
   就变成「匹配空字符串」，一进页面列表永远是空的。`AuditService.blankToNull()` 负责这一层，测试钉死。
2. **操作者名服务端联表**：审计表只存 `user_id`，页面直接显示数字没有意义。一次 `findAllById` 批量解析
   （不是逐行查），查不到给 `null` 而不是抛错——历史行的操作者可能早已不存在。
3. **动作下拉从接口拉**：`GET …/actions` 返回库里实际出现过的动作名。新增业务动作时下拉自动出现，
   不会因为「页面里漏写了一项」而漏筛。

**前端**

`features/admin/views/AdminAuditListView.vue`：三条件工具栏（动作/操作者 id/对象）+ 表格 + 分页 + 详情 popover
（`detailJson` 能解析时缩进美化，解析失败原样显示）。页面上**没有任何写操作按钮**，测试用断言钉住这一点。

`AdminShell` 从「单页面包屑」改为**顶栏标签页**（用户管理 / 审计日志）：管理端页面数量少，侧栏在这里是多余的一层结构，
标签页也天然回答了「我在哪一页」。

**契约**：`/api/v1/admin/audit-logs`（列表）、`/api/v1/admin/audit-logs/actions`（动作枚举）+ `AdminAuditItem` /
`AdminAuditPage` / `ResultAdminAuditPage` / `ResultStringList` 四个 schema。对外契约从 33 条增至 **35 条**。

**测试**：后端 `AuditServiceTest` 10 项（空过滤转 null、分页夹取、操作者解析、detail 原样、actions 去重排序）；
前端 `test/features/admin/audit-list.spec.ts` 11 项（空态、写入即留痕、密码不入 detail、三条件筛选、分页不重叠、
重置、只读断言）。

### 11.2 与设计的实现差异（4 处，均为改进）

| # | 设计写法 | 实际实现 | 原因 |
| --- | --- | --- | --- |
| 1 | 错误码 `40408/40904/40905` | **`40409/40905/40906`** | `40408`、`40904` 已被题库功能占用（见 §5.8 取号修正）。**设计文档写错了，实现按真实代码取号** |
| 2 | `AdminUserCreateRequest` 无 `role` 字段，靠 `additionalProperties:false` 挡 | **显式声明 `role` 字段 + service 层拒绝** | 实测发现全局 Jackson 是「忽略未知字段」：不声明则 `{"role":"ADMIN"}` 被**静默丢弃**，落库仍是 USER 但**契约承诺的 40001 没发生**——调用方会误以为设置成功。声明后报 `40001「不能指定角色，新建账号一律为普通用户」`，指向明确 |
| 3 | `UserRepository.findAnyByUsername` 等按方法名派生查询 | **显式 `@Query`** | `findByIdIncludingDeleted` / `findAnyByUsername` 的语义无法用派生命名表达（要绕开 `deleted` 过滤），派生会解析失败或语义错 |
| 4 | 审计 detail 记「变更字段快照」 | 记 `{"displayName":"changed"}` / `{"password":"changed"}` | 不记值更彻底：连显示名的旧值也不落库，避免审计表变成影子用户表 |
