### 旧提示词的适用修正

- 旧 J1 的依赖白名单只适用于骨架阶段，H1 可引入必要认证/哈希/校验依赖；继续使用既有 JPA + MVC/SseEmitter，不因文档旧称 WebClient 而替换当前客户端。
- 旧 J2 未要求资料所有者过滤；现增加归属、用户内哈希去重与批量状态的范围限定。资料更新字段使用 YAML 的 title/tags/version/status，不使用 enabled。
- 旧 J3 的 k 范围以当前契约 1–10 为准；不原样透传内部字段、不复用 Python messageId。成功落库后才发一次 done；失败发送 error。熔断可后置，连接/读取超时与资源释放不可后置。
- 旧 J4 参数错误码按当前契约：chunkSize 为 40002、overlap 为 40003；query 用 q。串行检查包含 PENDING/RUNNING 并原子化，不能只靠先查后建。
- 旧 A1 进程 dict 仅历史 mock 骨架；正式交付要求持久化执行状态及重启恢复。内部字段不统一强制 camelCase，严格遵守内部 YAML。
- 分块参数由 Java 校验并传入，两端默认值保持一致（现行为 180/30）；manifest 记录实际参数。500/75 可作显式实验配置，不因切换 Python 而隐式变更默认值。
- 缺认证 HTTP 401/code=40100；跨用户文档按既有契约 HTTP 404/code=40401。改变语义先更新契约及测试，不把 401/403 任意一个都当通过。
- 旧“只能测纯逻辑”的白盒限制取消：服务状态机、事务、故障与取消均需测试。MockMvc 与根 HTTP 黑盒分层验证，不视为重复浪费。
- 旧测试 INTERNAL_TOKEN 默认值移除，密钥由测试环境显式注入；原账户和固定 token 的正例改为正常登录，负例保留。旧阶段命令若缺 Authorization，执行时必须补真实登录 token。
- 旧 §16 表仅描述初建顺序；当前进度需根据门禁产物核实，不将源文件存在视为阶段完成。
> 用途：把《00_项目架构规格》《后端文档》《RAG文档》转译成**可直接投喂给 AI 编程工具的分阶段提示词**，并把「旧后端怎么删干净」「技术栈谁先开始」「每个功能怎么测」三件事钉死在文档里。
> 铁律：**每阶段做完必须过门禁（`test/` 下的测试全绿），门禁不过禁止进入下一阶段。**
> 配套上下文（开发时一并投喂）：`00_项目架构规格.md` §3/§7/§12、`后端文档.md`、`RAG文档.md`、`01-功能规格/F01~F11`、`docs/api/openapi-public.yaml` 与 `openapi-internal.yaml`（J0 产出）。

## 3. 技术栈启动顺序（谁先开始）

### 3.1 结论：**Java 先，Python 后，契约最先**

```
第 0 步  J0  契约冻结（两份 OpenAPI YAML + 信封 Schema + 错误码表）      ← 谁都不写代码，先定契约
第 1 步  J1  Java 骨架（信封 / 7 表 / 全局异常 / springdoc / Mock AiClient）
第 2 步  J2  Java 会话·消息·文档 CRUD
第 3 步  J3  Java SSE 透传 + 异步落库 + trace
第 4 步  J4  Java 建库编排 + 任务轮询 + NEEDS_REBUILD
第 5 步  J5  Java 评测三件套 + 反馈 + 候选池 + 实验 409
第 6 步  A1  Python 骨架 + 8 条内部接口 + mock provider        ← 到这一步 Python 才开工
第 7 步  J6  三端联调（前端 VITE_USE_MOCK=false + npm run regress 10 场景）
第 8 步  A2  Python 真 RAG 闭环（递归切分 + Milvus Lite + 引用）
第 9 步  A3  Python 效果基线（BM25 + RRF + Rerank + 查询改写）
```

### 3.2 为什么不先做 Python / 不先做 RAG

1. **只有 Java 那扇门是前端能敲的**。前端 28 个端点全在 `/api/v1`，Python 的 8 个 `/internal/v1/*` 前端一个都用不上。先做 Python 等于造了半栋楼没有门。
2. **Java 可以零外部依赖跑通全部 28 端点**。用 `MockAiClient` 推假 SSE（固定推 status→retrieval→token→done），前端立刻能 `VITE_USE_MOCK=false` 联调，比 MSW 更接近真实链路（真 axios、真 SSE、真落库）。
3. **RAG 调参需要测量装置，而测量装置在 Java**。E3 参数矩阵、F09 批量对照、C1 反馈闭环的数据全走 Java 的 `/eval/*`。先做 RAG 等于闭眼调参，只能靠肉眼看答案"感觉变好了"。
4. **三件最难的事与 Python 无关**：SSE 逐事件透传、Resilience4j 熔断降级成 direct、`doOnComplete` 异步落库。这些在 J3 就要解决，越晚做风险越大。

**唯一该改顺序的情况**：如果交付核心是「RAG 效果答辩」而不是「三端工程完整」，可以把 A1 提到 J1 之前——但 J0 契约仍然必须最先。

## 8. 阶段 J4：建库编排 + 任务轮询 + NEEDS_REBUILD

### 提示词 J4

```text
【任务】实现 4 条接口（GET /index/status、POST /index/rebuild、GET /index/tasks/{id}、GET /chunks）：
1. POST /api/v1/index/rebuild：body {chunkSize, overlap}。
   校验：50 ≤ chunkSize ≤ 1000（40001「片段长度需在 50–1000 之间」）；

3. GET /api/v1/index/status：返回 {status: ready|needs_rebuild|unavailable, chunkSize, overlap,

   - Python /internal/v1/index/status 不可达 → unavailable；
   - 其余 → ready。
4. GET /api/v1/chunks：支持 ?docId=&keyword=&kind= 三路过滤，返回 chunk 列表

5. 文档增删改、参数变更、嵌入模型变更 → 把受影响文档置 NEEDS_REBUILD。

【约束】
- 建库任务必须串行：已有 RUNNING 任务时再 POST rebuild 返回 409（40903「已有建库任务在执行」）。
```

### 14.1 分块默认值：180/30 还是 500/75

| 来源 | 值 |
|---|---|

**拍板规则（写进 A2 提示词）**：
- **Python 的默认值用 500/75**（技术上是更合理的切分粒度）。
- **但 manifest 必须如实记录本次实际用的 chunk_size / overlap**，`GET /api/v1/index/status` 原样返回。
- **前端一律以 manifest 返回值为准**（`normalizeIndexStatus` 已经读 `detail.chunkSize`），不硬编码。
- 因此 `frontend/src/constants/app.ts` 的 180/30 只作为「首次建库时的表单默认值」，不是真相来源。
- **如果前端首次建库不传参数，就用 Python 默认 500/75**；建库后状态灯显示的实际值是 500/75，前端不报错。

> 这样两边都不需要改常量，冲突自然消解。**但必须在 A2 阶段用测试锁死**：建库后 `/index/status` 的 chunkSize 必须等于 manifest 里记的值。

### 14.2 SSE 用 WebFlux 还是 MVC

**拍板：用 `spring-boot-starter-web` + `SseEmitter`，不用 WebFlux。** 理由：
- `~/.m2` 里没有 webflux，要联网拉一整套 reactor；web 已缓存。
- springdoc 对 MVC 支持更成熟（J1 就要出 Swagger UI）。
- `SseEmitter` 足够满足「逐事件 flush + 客户端断开感知」，且与 `@RestControllerAdvice` 兼容。
- **绝不能同时引 webflux 与 web**，会退化成 servlet 栈且 SSE 行为异常。

## 15. 卡关处理提示词（任意阶段门禁不过时用）

```text
阶段 {N} 门禁未通过。现在按以下顺序排查，不要跳步：
1. 贴出完整报错（含堆栈与失败用例的 assert 消息），不要只贴最后一行。
2. 判断失败类型：
   - 编译/类型错误 → 先修，不写新功能；
   - 契约不符（字段名/形状对不上 YAML）→ 先确认 YAML 是否已更新，再决定改代码还是改 YAML（**只能改一处**）；
   - 时序问题（轮询/SSE 卡住）→ 先加日志确认事件到底有没有到，不要直接加 sleep；
   - 环境问题（连不上库/端口占用/依赖拉不下来）→ 单独处理，不要混在业务修复里。
3. 给出最小复现命令（curl 或单条 pytest），让我能自己跑一次。
4. 修复后只重跑失败的那个测试文件，通过后再跑整个阶段目录。
5. 全程不许修改测试用例来"让它通过"——测试是用例契约，改测试必须先说明理由并征得同意。
```
