> 版本：v2.1（2026-10-30）

## 0. 对参考规格的裁剪决策（先看这张表）

| 参考规格条目 | 决策 | 理由 |
|---|---|---|
| Monorepo（frontend/server-java/server-ai/docs/api） | ✅ 采纳 | 结构清晰，契约先行 |
| 分层铁律（薄 Controller、DTO/Entity 分离、AiServiceClient 熔断） | ✅ 采纳 | 工程纪律与规模无关 |
| `/api/v1` 对外 + `/internal/v1` 内部 + 统一 Result + 错误码表 | ✅ 采纳 | 替代此前文档中的 `/api`、`/ai` 路径 |
| SSE 流式事件协议（retrieval/token/done/error） | ✅ 采纳 | 聊天体验核心，F04 直接受益 |
| 文档状态机（UPLOADING/PARSING/INDEXED/FAILED） | ✅ 采纳并扩展 | 增加 `NEEDS_REBUILD`（manifest 不一致 → 原 F3 待重建提示并入状态机） |
| 前端 feature-first + api 抽象层 + 双加载态 | ✅ 采纳 | F01-F10 映射到 features 目录 |
| RAG 组件接口化（Retriever/Reranker/LLMProvider/VectorStore + pipeline.py） | ✅ 采纳 | 与 RAG 文档既有设计一致 |
| 契约同步机制（openapi-public.yaml / openapi-internal.yaml 为源头） | ✅ 采纳 | 替代口头契约 |
| 禁止反模式清单 | ✅ 采纳并增补 | 见 §12 |
| MySQL 业务库 | ✅ 采纳 | docker-compose 起，成本低 |
| MinIO 对象存储 | 🔻 简化：本地磁盘卷 + `Storage` 接口抽象 | 当前知识库仅 6 个 md 文件；接口留好，MinIO 列为 P5 可选 |
| Redis + Celery/ARQ 任务队列 | 🔻 简化：FastAPI BackgroundTasks + 进程内任务表 + 轮询 | 建库是低频操作；Redis 列为 P5（语义缓存/热点会话时再引） |
| 向量库 Milvus 或 pgvector | 🔻 简化：Milvus Lite（嵌入式） | SDK 与生产 Milvus 一致，迁移只改连接串（既有决策） |
| Spring Security JWT 全套 + 配额 | 🔻 简化：阶段1 演示模式（固定用户），表结构与 SecurityConfig 预留 JWT | 单人/课堂场景；接口不返工 |
| K8s / GPU runtime | ❌ 暂缓 | LLM 走 API 调用，无本地推理需求 |
| LangChain(可选) | ✅ 明确：作组件库用，**不引入 LangGraph** | 管线为线性流程（既有决策） |
| ——（原规格没有）| ➕ 项目特有：三模式问答(rag/direct/both)、k 可调、检索过程面板、片段浏览(拓展B)、批量对照评测、manifest 机制、mock provider 联调 | 来自 01-功能规格 F01-F10，全部保留 |

## 2. 架构拓扑与铁律

```
┌─────────────┐
│  Vue 前端    │ ← 只对接 Java 网关，不直连 Python
└──────┬──────┘
       │ HTTPS / REST / SSE
┌──────▼──────────────────────┐
│  Java 业务服务（统一入口）    │
│  ├─ 鉴权(演示模式)·审计·配置  │
│  ├─ 会话与消息持久化          │
│  ├─ 文档元数据与状态机        │
│  └─ AiServiceClient(熔断)    │
└──────┬───────────┬──────────┘
       │           │
  ┌────▼───┐  ┌────▼─────────────────┐
  │ MySQL  │  │ Python AI 服务        │
  └────────┘  │  ├─ 离线：解析→切分→   │
  ┌────────┐  │  │   嵌入→入库(异步)   │
  │本地文档卷│◄─┤  ├─ 在线：改写→混合   │
  └────────┘  │  │   检索→RRF→重排→生成 │
              │  └─ Milvus Lite       │
              └──────────────────────┘
```

**架构铁律**（采纳原规格，增补 2 条）：

1. 前端只和 Java 通信；Python 不对外暴露端口，仅内网 + 内部 token 可达。
2. 鉴权、审计、配置只在 Java 做一份；Python 无状态、不存业务数据。
3. 所有模型/向量/Prompt 逻辑收敛在 Python，Java 不碰任何 AI 逻辑。
4. 会话历史、消息、文档元数据归 Java + MySQL；Python 只管向量库与解析。
5. （增补）**评测与对照实验也是一等公民**：`/internal/v1/eval` 与 eval_run 落库纳入契约，不是脚本外挂。
6. （增补）**mock provider 模式是联调契约的一部分**：Python 全链路可切 mock（无 LLM/Embedding key 也能跑通三端），CI 依赖它。

## 5. Java 业务服务结构（要点，详见《后端文档》）

```
server-java/.../app/
├── controller/      # AuthController / ConversationController / ChatController(SSE透传)
│                    # KnowledgeController / EvalController
├── service/         # ChatService / KnowledgeService / IngestService / EvalService / impl/
├── client/          # ★ AiServiceClient（WebClient + Resilience4j 熔断 + 内部token）+ dto/

├── config/          # SecurityConfig / WebClientConfig / AsyncConfig / CorsConfig
└── common/          # result(Result<T>) / exception(错误码表) / enums
```

**数据表**（在原规格基础上扩展项目特有字段）：

```sql
user(id, username, password_hash, role, created_at)            -- 阶段1 内置演示账号
conversation(id, user_id, title, created_at, updated_at)
message(id, conversation_id, role, content, mode, top_k,
        citations_json, retrieval_trace_json, usage_json,
        elapsed_ms, degraded, created_at)                      -- RAG 中间产物全落库
document(id, title, filename, storage_key, sha256, version,
         tags, status, error_msg, created_at)
-- status: UPLOADING / PARSING / INDEXED / FAILED / NEEDS_REBUILD / DISABLED
index_task(id, status, stage, progress, chunk_size, overlap,
           embedding_model, doc_count, chunk_count, error, created_at, finished_at)
eval_run(id, name, question_count, result_csv, summary_json, created_at)
audit_log(id, user_id, action, target, detail_json, created_at)
```

**状态机联动**：文档增删改 / 分块参数变更 / 嵌入模型变更 → 相应 document 置 `NEEDS_REBUILD` → Java 侧 manifest 摘要与 Python `/internal/v1/index/status` 比对 → 前端状态灯。

## 6. Python AI 服务结构（要点，详见《RAG 文档》）

```
server-ai/app/
├── main.py
├── api/                 # internal 路由：chat.py(SSE) / knowledge.py(parse/status/index) / eval.py / health.py
├── core/
│   ├── rag/
│   │   ├── pipeline.py      # ★ 编排：改写→双路召回→RRF→重排→组Prompt→生成
│   │   ├── loader.py / splitter.py / embedder.py
│   │   ├── retriever.py     # 接口 + 混合检索实现(向量+BM25+RRF)
│   │   ├── reranker.py / prompt.py
│   ├── llm/provider.py      # 抽象基类：openai_client / mock_client（★ mock 是联调契约）
│   └── vector_store/        # base.py + milvus_lite.py（接口化可替换）
├── services/            # chat_service / ingest_service(BackgroundTasks+任务表) / eval_service
├── schemas/             # Pydantic v2 内部契约模型
└── config.py            # Pydantic Settings（LLM_API_KEY / EMBEDDING_MODEL / MILVUS_URI 等）
```

**RAG 设计原则**（合并既有决策与原规格）：

1. 组件接口化 + 依赖注入组装进 pipeline，可替换是硬需求。
2. 离线入库与在线查询两条独立管道；任务队列阶段1 用 BackgroundTasks + 任务表，Celery/ARQ 列 P5。
3. Python 无状态；会话历史由 Java 每轮透传。
4. 框架边界：LangChain 只用切分器/Milvus 集成/LLM 客户端；RRF、混合检索、BM25 中文分词自行实现；**不引入 LangGraph**（P5 若做 Self-RAG 再评估）。

## 7. 接口契约

### 7.1 统一响应（Java→前端）

```json
{ "code": 0, "message": "success", "data": {}, "timestamp": 1730000000 }
```

### 7.2 路径约定

- 对外：`/api/v1/**`（Java，JWT 预留，阶段1 演示模式放行）
- 内部：`/internal/v1/**`（Python，仅内网 + `X-Internal-Token`）
- 服务地址用服务名：`AI_SERVICE_URL=http://server-ai:8000`

### 7.3 对外接口（前端 ↔ Java）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | /api/v1/auth/login | 登录（阶段1 演示账号） |
| GET/POST | /api/v1/conversations | 会话列表 / 新建 |
| DELETE | /api/v1/conversations/{id}/messages | F10 清空对话 |
| GET | /api/v1/conversations/{id}/messages | 历史消息 |
| POST | /api/v1/chat/stream | AI 对话（SSE；body 含 mode: rag/direct/both、k） |
| GET | /api/v1/messages/{id}/trace | F08 检索过程详情 |
| POST | /api/v1/documents | 上传文档（multipart） |
| GET | /api/v1/documents | 文档列表（含状态） |
| PUT/DELETE | /api/v1/documents/{id} | 启停用 / 删除 |
| GET | /api/v1/index/status | 建库状态（F03） |
| POST | /api/v1/index/rebuild | F02 重建（chunkSize/overlap） |
| GET | /api/v1/index/tasks/{id} | 建库进度轮询 |
| GET | /api/v1/chunks | 拓展B 片段浏览（过滤参数） |
| POST | /api/v1/eval/batch | F09 批量对照测试 |
| GET | /api/v1/eval/runs | 评测历史 |

### 7.4 内部接口（Java ↔ Python）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | /internal/v1/chat/stream | RAG 问答（SSE 流式） |
| POST | /internal/v1/documents/parse | 触发解析入库（异步，返回 task_id） |
| GET | /internal/v1/ingest/{task_id} | 任务进度 |
| GET | /internal/v1/documents/{id}/status | 解析状态 |
| GET | /internal/v1/index/status | manifest 摘要（模型/参数/一致性） |
| POST | /internal/v1/retrieve | 只检索不生成（F08/评测复用） |
| POST | /internal/v1/eval/batch | 批量对照评测 |
| GET | /internal/v1/health | 健康检查 |

### 7.5 SSE 事件协议（在原规格上扩展 RAG 信息）

```
event: status      data: {"stage":"rewriting"|"retrieving"|"reranking"|"generating"}
event: retrieval   data: {"citations":[{"ref":"D02-C001","docId":2,"docTitle":"02_借阅规则.md",
                          "headingPath":"02_借阅规则>续借规定","chunk":"...","start":120,"end":300,
                          "score":0.87,"stage":"rerank"}]}
event: token       data: {"content":"根据"}
event: done        data: {"messageId":123,"usage":{"promptTokens":850,"completionTokens":320},
                          "elapsedMs":2340,"degraded":false}
event: error       data: {"code":50001,"message":"AI service unavailable","fallback":"direct"}
```

> 保留原规格四类事件；`status` 细分 RAG 阶段支撑"检索中/生成中"双加载态与 F08 面板；`done.degraded=true` 表示 AI 服务降级走了 direct 模式。

### 7.6 契约同步机制

`docs/api/*.yaml` 为唯一源头：前端 openapi-typescript 生成 TS 类型；Java openapi-generator、Python datamodel-code-generator 各自生成。字段变更改 YAML，禁止两端手改漂移；`/v1/` 内禁止破坏性变更。

## 8. 数据流（聊天）

```
视图触发 → api/chat.stream
→ Java 鉴权(演示放行)/校验/取会话最近N轮 history
→ AiServiceClient 调 /internal/v1/chat/stream（SSE 透传，熔断保护）
→ Python: 改写→混合检索→RRF→重排→组Prompt→LLM 流式生成
→ Java: 逐事件转发前端 + doOnComplete 异步落库消息(含 citations/trace/usage)
→ 前端: status驱动加载态 → retrieval渲染引用徽标 → token流式 → done收尾
降级：熔断/Python不可用 → Java 以 direct 模式重发或不带检索提示，done.degraded=true
```

## 11. 禁止反模式（原规格全量保留 + 增补）

| 禁止事项 | 正确做法 |
|---|---|
| Python 写用户/权限逻辑 | 鉴权收敛 Java，Python 内网信任 + 内部 token |
| Java 调 embedding API / 写 Prompt | AI 逻辑收敛 Python |
| 前端直连 Python | 统一走 Java 网关 |
| RAG 组件写死在业务函数 | Retriever/Reranker/LLM/VectorStore 接口化 |
| 对话历史存 Python/向量库 | 会话/消息归 Java + MySQL |
| 上传文档同步等解析完 | 异步任务 + 状态机 |
| Entity 直出前端 / Controller 直连库 | DTO/VO 隔离、三层依赖 |
| 内部地址写 localhost | 服务名 + 配置注入 |
| （增补）Java 侧拼 RAG 请求细节（top_k 语义、上下文格式） | Java 只透传业务参数，RAG 语义归 Python |
| （增补）评测/建库逻辑写在脚本里脱离契约 | eval/ingest 全部服务化入契约 |
| （增补）跳过 YAML 直接改两端代码加字段 | 契约先行，YAML 为源头 |

## 12. 落地顺序（合并原"P1-P4"与"先链路后效果"原则）

| 里程碑 | 内容 | 验收 |
|---|---|---|
| M1 链路打通 | 三端骨架：Vue 登录 → Java JWT(演示) → 转发 Python echo + SSE 透传；mock provider 全链路 | compose 一键起，SSE 事件可达前端 |
| M2 最小 RAG 闭环 | 上传 md → 解析切片(递归+标题继承) → Milvus Lite 入库 → 提问返回带引用回答（此阶段纯向量即可） | F02/F04/F05 验收通过 |
| M3 契约与工程化 | 两份 OpenAPI 冻结、三端类型生成、CI、错误码表 | 契约变更走 YAML，CI 绿 |
| M4 体验完备 | SSE 双加载态、检索过程面板、模式/k/对照、建库进度与 NEEDS_REBUILD、片段浏览、清空对话 | F01-F10 全验收 |
| M5 效果基线 | 混合检索(BM25+RRF)+Rerank+查询改写、入库审核、RAGAS 式评估接入 | 对照评测优于 M2 基线 |
| P5 按需进阶 | 独立 Milvus / MinIO / Redis+语义缓存 / acl 过滤 / LangGraph(Self-RAG) | 规模或需求触发 |
