# 功能扩展清单（从玩具到产品）

> 版本：v1.0（2026-10-30）
> 背景：现状功能 = 单一知识库（6 份 md）+ 三模式问答 + 批量对照测试，检索与业务两条腿都短。
> 读法：所有功能按 v2 架构（Java 业务 / Python AI / Vue 前端）设计；"依赖"列标注是否需要 P5 基础设施（独立 Milvus / MinIO / Redis / 多用户 JWT）。
> 优先级：⭐ 越多越值得做；推荐直接看 §8 的三个套餐。

---

## 1. 知识库能力扩展（解决"只能吃 6 份 md"）

| # | 功能 | 说明 | 价值 | 难度 | 依赖 |
|---|---|---|---|---|---|
| A1 | **多格式文档接入** | PDF/Word/txt/网页 URL 解析入库；PDF 用布局感知解析（MinerU API 或 pymupdf），表格线性化 | ⭐⭐⭐ | 中 | 需 Storage 抽象升级（MinIO 提前） |
| A2 | **多知识库/笔记本** | 按主题建库（读书会/课程笔记/项目文档），collection 隔离，切换检索范围 | ⭐⭐⭐ | 中 | Milvus 多 collection（Lite 即支持） |
| A3 | 文档版本与增量更新 | 同名文档重传 → diff 后只重嵌变化块，省 token；版本历史回滚 | ⭐⭐ | 中 | 无 |
| A4 | 知识库健康度面板 | 重复/冲突/失效片段检测报告（教程 §8）；一键清理 | ⭐⭐ | 中高 | 无（离线 LLM 任务） |
| A5 | 全局摘要索引（规则卡） | 离线 LLM 通读全库生成"统计摘要卡"与"规则卡"，解决比例/资格类全局问题（教程 §11.1 两大失败案例的解法） | ⭐⭐⭐ | 低 | 无 |
| A6 | 网页剪藏/邮件收集入口 | 浏览器插件或转发邮件 → 进"待审核箱" → 人工确认入库（呼应 Proposer-Reviewer） | ⭐ | 中高 | 无 |

> **首推 A5**：一天能做完，直接让"黑猫白猫"式全局问题从答错变答对，答辩演示效果极好。

## 7. 明确不建议做的（防过度设计）

- **微调模型**：成本高收益低，RAG 路径已覆盖（教程 §1.4）；
- **本地 GPU 部署推理**：无硬件，API 足够；
- **全网爬虫采集**：合规风险 + 知识库投毒面扩大，超出个人项目边界；
- **插件系统/多租户 SaaS 化**：架构支持未来做，现在做是空转；
- **实时协同编辑知识库**：与"Git 化知识管理"路线冲突，收益低。

## 8. 推荐套餐（三选一或组合）

### 套餐一：答辩亮点包（约 1 周，全部无新依赖）—— **✅ 已选定，详细设计见《02_套餐方案_功能亮点包.md》**
`A5 全局摘要卡 + B1 追问推荐 + C1 反馈闭环 + E3 参数实验管理 + B3 结构化回答`
> 效果：全局问题答对、对话有来有往、评测滚雪球、调参看数据——每个都是演示时的"哇"点，且全部落在现有架构内。

### 套餐二：个人知识库工具（约 2-3 周）
套餐一 + `A1 多格式接入 + A2 多知识库 + C2 导出/收藏 + E2 成本监控 + B5 语音`
> 效果：从"演示项目"变成"你自己每天真的会用的工具"。

### 套餐三：读书会产品化（约 3-4 周）
套餐一 + `C3 多用户 + D1 活动日历 + D2 预约引导 + D3 荐书审核 + C4 分享`
> 效果：知识库 + 业务闭环 + 多用户，完整的小型产品，Java 后端的价值充分体现。

## 9. 落位建议

- 套餐一功能插在 **M4（体验完备）与 M5（效果基线）之间**或并行，不改架构；
- A1/A2 涉及存储与 collection 设计，建议在 **M2 定 schema 时预留字段**（kb_id、storage_key 已留）；
- D 类功能是 Java 侧新业务模块（ActivityService / ReviewService），正好填充 Java 后端"业务味"不足的问题；
- F 类一律放 P5，且必须先用 M5 的评估体系证明基线有效后再叠加。
