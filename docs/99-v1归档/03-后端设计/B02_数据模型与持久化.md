## 一、四类持久化对象

| 对象 | 位置 | 格式 | 谁写 | 谁读 | 生命周期 |
| --- | --- | --- | --- | --- | --- |
| 资料文件 | `data/*.md` `data/*.txt` | UTF-8（可带 BOM）纯文本 | 用户上传 / 手动放入 | `chunking.load_chunks`、`doc_stats` | 长期 |
| 向量索引 | `index.json` | JSON（UTF-8 **带 BOM**，`\n` 换行，`indent=2`） | `store.build_index` | `store.read_index` | 长期，重建覆盖 |
| 问答日志 | `logs/{YYYYmmdd-HHMMSS}-{hex6}.jsonl` | JSON Lines（UTF-8 带 BOM，每行一条） | `store.append_log` | `store.last_log`、前端「检索过程」 | 长期追加 |
| 批量导出 | `exports/对照测试_{YYYYmmdd-HHMMSS}.csv` | CSV（UTF-8 **带 BOM**，Excel 直接双击不乱码） | `batch.export_csv` | 用户 | 每次导出新增 |

内存态（不落盘）：`session._STATE`（会话）、`store._BUILD_STATE`（建库进度）、`batch._STATE`（批量进度）、
`settings._MEMORY_KEYS`（密钥）。

**实测数值**：`index.json` = 106 896 B，`chunks` 15 条，每条 `embedding` 256 个 float，
`manifest.sources` 6 条（按文件名升序，`chunking.load_chunks` 里 `sorted` 保证）。

### 2.1 `manifest` 五个字段的作用

| 字段 | 来源 | 变更后会发生什么 |
| --- | --- | --- |
| `embedding_model` | `cfg["embedding_model"]`（mock 档为 `""`） | 换模型 → 向量空间变了 → `read_index` 判定 stale |
| `embedding_endpoint` | `cfg["embedding_endpoint"]` | 同上（换了服务商即换了向量） |
| `chunk_size` | `cfg["chunk_size"]` | 片段边界变了 → 全部 `start`/`end`/`text` 失效 |
| `chunk_overlap` | `cfg["chunk_overlap"]` | 同上 |
| `sources[].sha256` | `chunking.load_chunks` 对 `read_doc` 的结果算 | 资料内容被改 → 片段与原文对不上 |

**manifest 是 F3「资料或分块设置改变后提示需要重新建库」的全部技术依据**。
它不存时间戳、不存版本号，只存「影响向量结果的最小充分信息集合」——
时间戳会因为无意义的重新保存而误报，版本号需要额外维护，两者都不如内容哈希准确。

### 2.2 `chunks` 七个字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `chunk_id` | str | `D{资料序号:02d}-C{片段序号:03d}`，如 `D02-C001`。**资料序号按文件名升序**，片段序号从 1 开始 |
| `source` | str | 文件名（不含目录），如 `02_借阅规则.md` |
| `start` | int | 0-based 起始下标（含） |
| `end` | int | 0-based 结束下标（**不含**），恒有 `end - start == len(text)` |
| `text` | str | 片段正文（`text[start:end]` 的副本） |
| `verified` | bool | `source not in UNVERIFIED_SOURCES` |
| `embedding` | list[float] | 256 维（mock）或接口返回维度（real），L2 归一后存 |

**`start`/`end` 是拓展B 的全部依据**：前端「片段浏览」把 `start+1` 与 `end` 显示成
「第 N 字至第 M 字」（`app/api.py:129-138` 里的 `position` 字段），
相邻片段因为 `overlap=30` 必然出现 `end[i] > start[i+1]`，这就是「能看到重叠文字」。

## 三、`build_index` 的原子写

```python
# app/store.py:33-86（节选）
chunks, sources = chunking.load_chunks(DATA_DIR, size, overlap)
vectors = []
for i in range(0, len(chunks), batch):
    part = embedding.embed_texts(cfg, key, [c["text"] for c in chunks[i:i + batch]])
    vectors.extend(part)
    if progress:
        progress(done=len(vectors), total=len(chunks))
for chunk, vector in zip(chunks, vectors):
    chunk["embedding"] = vector

payload = {"manifest": chunking.manifest_for(cfg, sources), "chunks": chunks}
with tempfile.NamedTemporaryFile(
    mode="w", encoding="utf-8-sig", newline="\n",
    dir=INDEX_FILE.parent, prefix=INDEX_FILE.name + ".", suffix=".tmp", delete=False,
) as temporary:
    json.dump(payload, temporary, ensure_ascii=False, indent=2, allow_nan=False)
temporary.replace(INDEX_FILE)
```

四个关键点：

1. **临时文件必须与目标同目录**（`dir=INDEX_FILE.parent`）：`Path.replace` 只在同一文件系统内才是原子的，
   跨盘会退化成「复制 + 删除」，中途断电就留下半个文件。
2. **`encoding="utf-8-sig"`**：写入时自动加 BOM，与骨架 `rag_core.py` 的编码约定一致；
   `read_index` 用同样编码读，Windows 记事本打开也不会乱码。
3. **`allow_nan=False`**：向量里一旦出现 `NaN`/`Infinity`，`json.dump` 直接抛错而不是写出非法 JSON。
   这是 `embedding._validate_vectors` 之外的第二道闸。
4. **`ensure_ascii=False`**：中文直接写 UTF-8，不转 `\uXXXX`，文件可读、体积小一半。

**为什么不用 SQLite**：指导书任务1 要求「建库时把每个片段转为向量保存」，
单文件 JSON 让学生能用记事本直接看到 `embedding` 数组，比数据库更符合「可观察」的教学目标；
15 片段 106 KB 的规模也不需要索引结构。

## 四、`read_index` 的五层校验

```python
# app/store.py:119-153（逻辑顺序）
1. INDEX_FILE.exists()                    → 否：「尚未建库，请先点击“重新建库”。」
2. json.load(utf-8-sig) 且是 dict 且含 manifest/chunks
                                          → 否：「index.json 已损坏，请重新建库。」
                                              「index.json 结构不符，请重新建库。」
3. manifest == manifest_for(cfg, 当前 sources) 全等
                                          → 否：「资料、分块或嵌入模型已改变，请重新建库。」
4. len(chunks) 与逐片段字段全等
                                          → 否：「知识库片段字段不符，请重新建库。」
5. 每条 embedding 长度一致
                                          → 否：「知识库向量维度不一致，请重新建库。」
```

### 第 3 层的「全等」是什么意思

不是比较 `manifest` 里某几个字段，而是**用当前配置和当前资料重新算一份 manifest，然后整字典 `==`**。
所以只要发生下列任一变化，都会立刻 stale：

- `data/` 里增删了文件（`sources` 长度或名字变了）；
- 某个 `.md` 的内容改了哪怕一个字（`sha256` 变了）；
- 界面把片段长度从 180 改成 120（`chunk_size` 变了）；
- `config.json` 换了 `embedding_model`。

### 第 4 层为什么要逐片段比对

只看「片段数是否相等」是不够的：把 180 改成 120 再改回 180，片段数还是 15，
但若资料在中间被改过，`start`/`end`/`text` 就全错位了。逐字段比对能抓出这种情况。

```python
expected_fields = {"chunk_id", "source", "start", "end", "text", "verified"}
for got, want in zip(index["chunks"], expected):
    if set(got) != expected_fields | {"embedding"}:
        raise AppError("知识库片段字段不符，请重新建库。")
    for field in expected_fields:
        if got[field] != want[field]:
            raise AppError("知识库片段字段不符，请重新建库。")
```

`expected` 是**现场用当前配置重切一遍**得到的结果（`chunking.load_chunks` 会再算一次 sha256）。
这意味着 `read_index` 的代价是「重新读 6 个文件 + 重切 15 个片段」，实测 < 5 ms，完全可接受。

### 字段用途对照

| 字段 | 前端/报告里用来做什么 | 思考题相关 |
| --- | --- | --- |
| `retrieved` | 「检索过程」表的全部行（含 `rank`/`score`/`retrieved` 标记） | 思考题2「k 是不是越大越好」——改 k 后对比这份数据 |
| `messages` | 「检索过程」第二张表（角色/内容） | 实验步骤第4步「发给模型的内容由哪些部分组成」——答案就是这张表 |
| `top_k`/`chunk_size`/`chunk_overlap` | 报告里说明「这一轮用的什么参数」 | 思考题1/2 的对照条件 |
| `usage` | 报告里可写「prompt 859 tokens」 | — |
| `status` | 失败时是 `"error: <文案>"`，失败**不入 history** | — |

### `status` 的两种取值

```python
# 成功：app/chat.py:88 之后
record["status"] = "ok"
# 失败：app/chat.py:70 附近，捕获 AppError 后写日志但**不 append_turn**
record["status"] = f"error: {exc}"
```

**为什么失败也要写日志**：报告里要能复盘「哪一次为什么失败」（比如 401 密钥过期），
而且失败不写日志的话，「检索过程」视图会显示上一次成功的内容，容易误判。

## 六、`session._STATE`（内存，91 行模块）

```python
# app/session.py:13-18
_STATE = {
    "session_id": uuid4().hex[:12],   # 12 位十六进制，如 "11a9005b1f12"
    "history": [],                    # [{"role": "user"/"assistant", "content": "..."}]
    "mode": "rag",                    # rag / direct / both
    "k": K_DEFAULT,                   # 3
}
```

| 操作 | 对 `session_id` | 对 `history` | 对 `mode`/`k` |
| --- | --- | --- | --- |
| `new_session()`（清空对话） | **换新** | **清空** | 保持不变 |
| `set_params(mode=...)` | 值变化时换新 | 值变化时清空 | 更新 |
| `set_params(k=...)` | 值变化时换新 | 值变化时清空 | 更新 |
| `append_turn(...)` | 不变 | 追加 user + assistant | 不变 |
| `set_history(h)` | 不变 | 覆盖（`both` 模式还原用） | 不变 |

**「换 mode 或 k 就清空 history」是刻意的**：任务3 要对比两种模式，
如果带着上一轮「查资料」的回答去问「不查资料」，direct 侧就等于偷看了知识库，对照就不成立。
同理任务4 要对比 k=1 与 k=3，必须干净重来。

**拓展A 的验收点在这里**：先问「本次会话的代号是青禾」→ 点清空 → 问「我刚才告诉你的代号是什么？」。
`new_session()` 把 `history` 清成 `[]`，下一轮 `build_rag_messages` 的 `*history` 展开为空，
模型（或 mock 规则）拿不到任何上下文，只能回答「当前请求未提供代号」。实测通过。
