### 1.2 两条通往 400 的路径

```python
# app/api.py:23 —— 路由内 try/except 手动转换
def _fail(exc: AppError) -> HTTPException:
    return HTTPException(status_code=400, detail=str(exc))

@app.post("/api/chat")
def api_chat(body: ChatIn) -> dict[str, Any]:
    try:
        result = chat.chat(body.question, body.mode, body.k)
    except AppError as exc:
        raise _fail(exc) from None
    ...
```

```python
# app/api.py:294 —— 兜底处理器（理论上不该被触发，因为每条路由都自己转了）
@app.exception_handler(AppError)
def app_error_handler(_request, exc: AppError) -> JSONResponse:
    return JSONResponse(status_code=400, content={"detail": str(exc)})
```

**为什么两套都留**：路由内转换能精确控制「哪条路由抛什么」；
兜底处理器保证「以后新加路由忘了写 try/except 也不会变成 500」。

### 1.3 直接抛 `HTTPException` 的两处

```python
# app/api.py:87  资料不存在
raise HTTPException(status_code=404, detail=f"找不到资料 {safe}")

# app/api.py:247  片段长度越界（在落盘前拦下）
raise HTTPException(status_code=400, detail="片段长度须在 50 至 1000 之间。")
```

`POST /api/config` 的校验**故意不用 `AppError`**：它发生在 `save_config_patch` 之前，
语义是「请求参数不合法」而不是「业务规则不满足」，用 400 + 直接 detail 更贴近 REST 惯例。
文案与前端 `ChunkSettings.vue` 里的本地校验**逐字一致**，所以用户无论在哪一层被拦，看到的都是同一句话。

## 二、`read_index` 的六条错误文案

```python
# app/store.py:119-153
"尚未建库，请先点击“重新建库”。"          # index.json 不存在
"index.json 已损坏，请重新建库。"          # json.load 失败
"index.json 结构不符，请重新建库。"        # 不是 dict / 缺 manifest 或 chunks
"资料、分块或嵌入模型已改变，请重新建库。"   # manifest 全等比对失败
"知识库片段字段不符，请重新建库。"          # 逐片段字段比对失败
"知识库向量维度不一致，请重新建库。"        # embedding 长度不一致
```

**六条都以「请重新建库」收尾**，这是刻意的：所有 stale 情形的用户动作都是同一个——
点一次「重新建库」。不需要用户理解 manifest 是什么。

`status()` 会把异常文案塞进 `message` 字段，前端渲染在「重新建库」按钮下方的 `.hint` 里。

## 三、`status()` 的 `ready` / `stale` 判定

```python
# app/store.py:155（结构）
def status() -> dict[str, Any]:
    ...
    try:
        index = read_index()
        ready, stale, message = True, False, ""
    except AppError as exc:
        ready, stale, message = False, True, str(exc)
        if "尚未建库" in message:
            stale = False          # 从没建过库，不算「需要重建」
    ...
```

三态对应前端徽章（v1 在 `web/src/store.js:kbBadge`，现行在 `frontend/src/app/layout/StatusLight.vue` + `frontend/src/stores/systemStatus.ts`）：

| `ready` | `stale` | 徽章文案 | class |
| --- | --- | --- | --- |
| `true` | `false` | `知识库就绪 · 15 片段` | `badge`（青绿） |
| `false` | `true` | `需要重新建库` | `badge warn`（琥珀） |
| `false` | `false` | `知识库未建库` | `badge bad`（红） |

**「从没建过库」与「建过但失效」必须区分**：前者用户该去建库，后者用户该去重建库。
靠 `"尚未建库" in message` 判断虽然土，但只有一处需要，不值得为此加一个枚举字段。

## 四、日志：写什么、不写什么

### 4.1 成功路径（`app/chat.py:88` 之后）

19 个字段，完整示例见 `docs/03-后端设计/B02_数据模型与持久化.md` 第五节。

### 4.2 失败路径

```python
# app/chat.py:70 附近
except AppError as exc:
    store.append_log({
        ..., 
        "question": question,
        "retrieved": [],
        "messages": messages,
        "answer": "",
        "usage": None,
        "elapsed_ms": ...,
        "status": f"error: {exc}",
    })
    raise
```

**失败也写日志**的三个理由：

1. 报告里要能复盘「哪一次为什么失败」（如 401 密钥过期、endpoint 写错）；
2. 不写的话「检索过程」视图会一直显示上一次成功的内容，容易误判；
3. `messages` 字段在失败时也有价值——能看出「当时发给模型的是什么」。

### 4.3 不写日志的场景

| 场景 | 是否写日志 | 原因 |
| --- | --- | --- |
| 批量对照（`batch._one`） | **不写** | `chat.answer_once(..., log=False)`。10 题 × 2 模式 = 20 条日志会把 `logs/` 刷满，而且批量结果本身有 CSV |
| `direct` 模式成功 | 写 | 需要在「检索过程」里看到 `retrieved: []` |
| 建库 | 不写 | 建库结果体现在 `index.json` 与 `_BUILD_STATE` |
| 上传/删除资料 | 不写 | 文件系统本身就是记录 |

### 4.4 日志文件的组织

```
logs/20261030-104357-bb68f2.jsonl    5630 B
logs/20261030-104649-c856fe.jsonl    7085 B
```

文件名 `{YYYYmmdd-HHMMSS}-{hex6}.jsonl`。**每次 `import app.api` 启动时新建一个文件**
（`store.touch()` 在 `ensure_dirs()` 之后调用），同一次运行的所有问答追加到同一个文件。
`hex6` 是随机后缀，防止同一秒内两次启动撞名。

`last_log()` 取「按文件名排序的最后一个文件的最后一行」：

```python
# app/store.py:202
def last_log() -> dict[str, Any]:
    files = sorted(LOG_DIR.glob("*.jsonl"))
    if not files:
        return {}
    lines = files[-1].read_text(encoding="utf-8-sig").strip().splitlines()
    return json.loads(lines[-1]) if lines else {}
```

### 5.4 三个值得单独说的断言

**① 篡改 manifest 验证 stale**（`tools/selfcheck.py:184-190`）

```python
index = store.read_index()
index["manifest"]["chunk_size"] = 999
store.INDEX_FILE.write_text(json.dumps(index, ensure_ascii=False), encoding="utf-8")
state2 = store.status()
check("改 manifest 后提示需要重建", state2["stale"] or not state2["ready"], state2["message"][:40])
store.build_index()          # 复原，不留下被篡改的 index.json
```

这条**真的去改 `index.json` 再恢复**，不是 mock。它验证的是 F3 的核心机制。

**② T09 的「不采信」判定**

```python
check("T09 不采信「完全免费」",
      "完全免费" not in fee["answer"] or "未经核实" in fee["answer"],
      fee["answer"][:70])
```

判定条件写成「不含完全免费 **或** 含未经核实」，是因为两种正确行为都算通过：
完全不提这件事，或者提到但明确标注「未经核实」。**只有「直接说完全免费」才是失败**。

**③ k=1 vs k=3 的对照**

```python
k1 = chat.chat("去参加周六读书会活动几点结束，同时最多能借几本普通图书？", "rag", 1)
k3 = chat.chat("去参加周六读书会活动几点结束，同时最多能借几本普通图书？", "rag", 3)
check("k=3 能答全 T07 两个要点", "16:00" in k3["answer"] and "4本" in k3["answer"], ...)
check("k=1 取回片段更少", len(k1["citations"]) == 1 and len(k3["citations"]) == 3, ...)
```

注意这里的问题比 `questions.csv` 里的 T07 **多了一个逗号**（`几点结束，同时`）。
刻意的：证明要点抽取不依赖标点的精确匹配。

## 八、常见故障对照表（对应指导书附录B）

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 页面显示「前端产物缺失」 | 没构建或 `frontend/dist` 被删 | `cd frontend && npm install && npm run build` |
| 上传报 `Form data requires "python-multipart"` | 缺依赖 | `py -3.12 -m pip install python-multipart` |
| 401 / 403 | 密钥错或未生效 | `POST /api/keys` 重新加载；或设 `RAG_CHAT_KEY` 环境变量 |
| 中文乱码 | 终端/文件编码 | 命令行加 `-X utf8`；PowerShell 读文件用 `py -3.12` |
| 回答没有来源编号 | 用了 direct 模式，或 real 档模型没遵守规则 | 切回 rag；检查 `SYSTEM_PROMPT` 第 1 条是否被改 |
| 资料外问题也作答 | real 档模型不听话 | 强化 `SYSTEM_PROMPT` 第 2 条；mock 档不受影响 |
| 被「完全免费」带偏 | 未启用可信度标注 | 确认 `UNVERIFIED_SOURCES` 含 `06_成员留言摘录.md` |
| 跨文档答不全 | k 太小 | 看「检索过程」排名，调大 k 或减小片段长度 |
| 建库慢或 413 | 批量太大 | 调小 `embedding_batch_size`（默认 8） |
| 端口被占 `[Errno 10048]` | 旧进程没退 | `Stop-Process -Id <PID> -Force`，或改 `config.json` 的 `port` |
